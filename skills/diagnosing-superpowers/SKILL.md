# การวินิจฉัย Superpowers

## ภาพรวม

ร่วมกับ human partner ระบุให้ชัดว่า session มีปัญหาอะไร อ่าน transcript บนดิสก์ และรายงานสิ่งที่เกิดขึ้นพร้อมหลักฐาน คุณรายงาน คุณไม่ได้วินิจฉัย superpowers ผู้คัดแยก bundle หรือ issue เป็นคนตัดสินว่า superpowers จะเปลี่ยนหรือไม่

**หลักการ:** ทุกข้อค้นพบต้องอ้าง `path:line` ไม่มีการอ้างอิง = ไม่ใช่ข้อค้นพบ ตัวเลขทุกตัวมาจาก transcript หรือคำสั่งที่คุณรัน ไม่ใช่จากความจำ

## ขั้นตอน

สร้าง todo หนึ่งรายการต่อหนึ่งขั้น ขั้น 5–7 รันเฉพาะเมื่อเข้าเงื่อนไขที่ระบุ

1. **รับเรื่องปัญหา** ถามทีละคำถามจนเขียนข้อความที่ระบุได้ว่า session ไหน, ช่วง turn ไหน (ถ้ารู้), partner คาดหวังอะไร, เกิดอะไรขึ้น และสิ่งที่พวกเขาสนใจวัดได้ (เวลาจริง, token, การกระทำซ้ำ, การกระทำเฉพาะอย่าง) "ช้าไป" คือคำบ่น ไม่ใช่ข้อความปัญหา จดไว้ด้วยว่าเป้าหมายคือรายงานบั๊กของ superpowers หรือไม่
2. **ค้นหา** แปลงแต่ละ session เป็นพาธสัมบูรณ์บนระบบไฟล์ที่ตรวจแล้ว โดยใช้ `references/session-discovery.md` ยืนยัน session ในอดีตด้วยการยกข้อความ prompt แรกและเวลา และระบุผู้สมัครทุกตัวที่ปฏิเสธพร้อมเหตุผล หรือ "ไม่มี" ระบุ transcript ของ subagent ทั้งหมด สร้าง `~/.super-ripple/diagnosing-superpowers/<session-id>/` บอกพาธให้ partner และกรอก `templates/case.md` ที่นั่น โดยทำตามกฎที่มาของข้อมูลสำหรับการสังเกตสภาพแวดล้อมและ skill
3. **คัดแยก** อ่านบริเวณรอบปัญหาที่รายงานด้วยตัวเอง จากนั้นส่ง subagent นักวิเคราะห์หนึ่งตัวต่อมิติ แบบคู่ขนาน โดยแต่ละตัวได้พาธไฟล์ case, `prompts/analyst-common.md` และไฟล์มิติหนึ่งไฟล์จาก `prompts/`: `skill-timeline.md`, `plan-adherence.md`, `repeated-work.md`, `stumbles.md`, `quality-evidence.md`, `request-conflicts.md`, `cost-and-time.md` แบ่งมิติตามช่วง turn เมื่อ transcript ยาว ทิ้งข้อค้นพบที่ส่งกลับมาโดยไม่มี `path:line`
4. **รายงาน** กรอกทุกส่วนของ `templates/report.md` ตามลำดับ เขียนลง workspace แสดงให้ดู และบอกพาธ ตรวจว่าเนื้อหาที่อ้างพิสูจน์อะไรได้จริง และเก็บหลักฐานสนับสนุนไว้ symlink alias ไม่ใช่สำเนาซ้ำซ้อน
5. **GitHub issues** — เมื่อรายงานข้อ 7 ระบุว่าเป็นไปได้หรือน่าจะใช่ หรือ partner ขอ ค้นหา issue ที่เปิดและปิดแล้วตามอาการโดยใช้ `references/github-issues.md` แสดงรายการที่ตรงและแนะนำให้เพิ่มรายงานเข้าไปใน issue ที่ใกล้ที่สุด ถ้าไม่มีที่ตรง ให้กรอก `templates/issue.md` เขียนลง workspace แสดงข้อความที่แน่นอน และสร้าง issue หลังได้รับอนุมัติเท่านั้น `gh` แนบไฟล์ไม่ได้ ถ้ามี bundle ให้บอกพาธเพื่อให้ partner แนบเองในเบราว์เซอร์
6. **ส่งออก** — เมื่อ partner ขอ bundle เท่านั้น ห้ามสร้างโดยไม่ได้ขอ ถ้าเป้าหมายตอนรับเรื่องคือรายงานบั๊ก ให้บอกครั้งเดียวว่ามี bundle ที่ลบข้อมูลสำคัญแล้วให้เมื่อขอ แล้วรอ ถามระดับการปกปิด โดยบอกว่าแต่ละระดับรวมอะไร: skeleton (ไม่มีเนื้อหา tool-result), evidence (มีเนื้อหาเฉพาะเหตุการณ์ที่อ้าง), full สร้าง bundle ตาม `templates/bundle-README.md` ส่ง `prompts/scrub.md` แล้วตามด้วย `prompts/scrub-audit.md` ทำซ้ำทั้งคู่จนการตรวจสอบคืนค่า CLEAN ทำการตรวจหลักฐานและกระทบยอดของเทมเพลต bundle ให้เสร็จ ก่อนแสดง scrub log สุดท้าย รายการไฟล์ และผลด้านความเป็นส่วนตัวและหลักฐาน บีบอัด (`zip -r` หรือ `tar -czf`) หลังได้รับอนุมัติเท่านั้น เมื่อให้พาธไฟล์บีบอัด ให้บอกว่ามีอะไรบ้าง ชี้ไปที่ scrub log สำหรับสิ่งที่ถูกแทนที่ และบอกว่าการลบข้อมูลอาจตกหล่น: ต้องตรวจทุกไฟล์ก่อนแชร์
7. **Session ที่คล้ายกัน** — เมื่อถูกขอ แปลงข้อค้นพบที่ยืนยันแล้วเป็นลายเซ็น รายการผู้สมัครตาม mtime และขนาด หาเลขบรรทัดของเครื่องหมาย ส่ง `prompts/similar-session.md` ต่อผู้สมัครแบบคู่ขนาน และต่อท้ายรายงานข้อ 9

## ตารางอ้างอิงด่วน

นักวิเคราะห์ทั้งเจ็ดรันเสมอ ตารางนี้บอกว่าควรอ่านบริเวณไหนเองในขั้น 3 และควรนำข้อค้นพบไหนขึ้นต้นในข้อสรุป

| คำบ่น | อ่านก่อน, นำด้วย |
|---|---|
| "ช้าไป" | cost-and-time, stumbles |
| "ทำไมมันทำงานเพิ่มแบบนี้?" | repeated-work, plan-adherence |
| "ทำไมแพงจัง?" | cost-and-time |
| "มันกำลังทำบ้าอะไรอยู่?" (ยังรันอยู่) | skill-timeline; จดว่ากำลังดำเนินอยู่ในส่วนความครอบคลุม |
| "มันไม่ทำตามแผน" | plan-adherence, บรรทัด compaction ก่อน |
| "Skill X ไม่ทำงานเลย" | skill-timeline |

## กฎเหล็ก

- **ความปลอดภัยของ context** บรรทัดเดียวใน transcript อาจใหญ่ถึงเมกะไบต์ ทำตาม `references/context-safety.md` กับทุกไฟล์ session ทุกครั้ง
- **อ่านอย่างเดียว** ห้ามแก้ ย้าย หรือลบไฟล์ session
- **ส่งพาธที่แน่นอนให้ subagent** "session ปัจจุบัน" ของ subagent คือของมันเอง ส่งพาธสัมบูรณ์และ id
- **เฉพาะ prompt ของมนุษย์** ผลลัพธ์ของ hook, system reminder และผลของ tool ไม่ใช่คำพูดของ partner ใน transcript ของ subagent "user" คือ agent แม่
- **ห้ามวินิจฉัย superpowers** รายงานข้อ 7 ระบุการเกี่ยวข้องแล้วหยุด ห้ามระบุข้อบกพร่องใน skill หรือเสนอการเปลี่ยนแปลง การที่ partner กดดันขอวิธีแก้ไม่ได้ยกเว้นกฎนี้ ให้ชี้ไปที่ขั้น issue และบอกว่ามี bundle เมื่อขอ ห้ามให้คำแนะนำแก่ partner ด้วย
- **ด่านอนุมัติ** ห้ามบีบอัดก่อนที่ partner จะเห็น scrub log และรายการไฟล์ ห้ามสร้าง issue หรือคอมเมนต์ก่อนที่พวกเขาอนุมัติข้อความที่แน่นอน และห้ามใช้สรุปที่เป็น placeholder
- **รับเรื่องก่อนวิเคราะห์** ห้ามเริ่มขั้น 2–7 จนกว่า partner จะตอบ ถ้าพวกเขาไม่อยู่ ให้เขียนคำถามแล้วหยุด ข้อความที่คุณสร้างแทนพวกเขาไม่ใช่คำตอบ คำขอที่กำหนดขอบเขตแล้ว — เหตุการณ์เฉพาะ, สิ่งที่กำลังรัน หรือการวิเคราะห์ที่จะรัน — ถือเป็นข้อความปัญหาอยู่แล้ว: ตอบ แล้วค่อยถาม "ทำไม" ของทั้ง session คือคำบ่น

## สัญญาณเตือน

| ความคิด | ความจริง |
|---------|---------|
| "ปัญหาชัดอยู่แล้ว ข้ามการรับเรื่อง" | ข้อความปัญหากำหนดขอบเขตทุกอย่าง ถามซะ |
| "พวกเขาไม่อยู่ เลยสร้างข้อความเอง" | คุณสร้างสิ่งที่พวกเขาต้องการไม่ได้ เขียนคำถามแล้วหยุด |
| "กวาดทุกอย่างเลยแล้วค่อยถามตอนท้าย" | การกวาดที่ไม่กำหนดขอบเขตใช้งบของพวกเขากับคำถามผิด ถามก่อน |
| "พวกเขาอยากได้รายงานบั๊ก สร้าง bundle เลย" | bundle คือข้อมูล session ของพวกเขาที่ถูกแพ็ก สร้างเมื่อพวกเขาขอเท่านั้น |
| "แก้เล็กๆ เจาะจง ไม่ต้องปรับโครงสร้าง" | ไม่ใช่การตัดสินใจของคุณ ไม่ว่าจะเล็กแค่ไหน รายงานหลักฐาน ผู้คัดแยกเป็นคนตัดสิน |
| "ราคาต่อ token เป็นที่รู้กันดี" | ตัวเลขที่ไม่ได้คำนวณจาก transcript คือของที่แต่งขึ้น อ้างอิงหรือทิ้ง |
