# การใช้ Git Worktrees

## ภาพรวม

ให้แน่ใจว่างานเกิดขึ้นใน workspace ที่แยกต่างหาก ให้ใช้เครื่องมือ worktree เนทีฟของแพลตฟอร์มก่อน ถอยไปใช้ git worktree แบบทำเองเฉพาะเมื่อไม่มีเครื่องมือเนทีฟ

**หลักการ:** ตรวจหาการแยกที่มีอยู่แล้วก่อน จากนั้นใช้เครื่องมือเนทีฟ แล้วค่อยถอยไปใช้ git ห้ามขัดกับ harness

**ประกาศตอนเริ่ม:** "ผมใช้ skill using-git-worktrees เพื่อตั้งค่า workspace ที่แยกต่างหาก"

## ขั้น 0: ตรวจหาการแยกที่มีอยู่

**ก่อนสร้างอะไร ให้ตรวจก่อนว่าคุณอยู่ใน workspace ที่แยกแล้วหรือยัง**

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
BRANCH=$(git branch --show-current)
```

**ป้องกัน submodule:** `GIT_DIR != GIT_COMMON` เป็นจริงภายใน git submodule ด้วย ก่อนสรุปว่า "อยู่ใน worktree แล้ว" ให้ตรวจว่าไม่ได้อยู่ใน submodule:

```bash
# ถ้าคำสั่งนี้คืนพาธ แปลว่าอยู่ใน submodule ไม่ใช่ worktree — ปฏิบัติเหมือน repo ปกติ
git rev-parse --show-superproject-working-tree 2>/dev/null
```

**ถ้า `GIT_DIR != GIT_COMMON` (และไม่ใช่ submodule):** คุณอยู่ใน linked worktree แล้ว ข้ามไปขั้น 2 (ตั้งค่าโปรเจกต์) ห้ามสร้าง worktree ซ้อน

รายงานพร้อมสถานะ branch:
- อยู่บน branch: "อยู่ใน workspace ที่แยกแล้วที่ `<path>` บน branch `<name>`"
- Detached HEAD: "อยู่ใน workspace ที่แยกแล้วที่ `<path>` (detached HEAD, จัดการจากภายนอก) ต้องสร้าง branch ตอนจบงาน"

**ถ้า `GIT_DIR == GIT_COMMON` (หรืออยู่ใน submodule):** คุณอยู่ใน checkout ปกติของ repo

ผู้ใช้ระบุความต้องการเรื่อง worktree ไว้ในคำสั่งแล้วหรือยัง? ถ้ายัง ให้ขอความยินยอมก่อนสร้าง:

> "ต้องการให้ผมตั้งค่า worktree แยกไหม? มันช่วยปกป้อง branch ปัจจุบันของคุณจากการเปลี่ยนแปลง"

ถ้ามีความต้องการที่ประกาศไว้แล้ว ให้ทำตามโดยไม่ต้องถาม ถ้าผู้ใช้ปฏิเสธ ให้ทำงานในที่เดิมและข้ามไปขั้น 2

## ขั้น 1: สร้าง Workspace ที่แยกต่างหาก

**คุณมีสองกลไก ลองตามลำดับนี้**

### 1a. เครื่องมือ Worktree เนทีฟ (แนะนำ)

ผู้ใช้ขอ workspace ที่แยกแล้ว (ยินยอมในขั้น 0) คุณมีวิธีสร้าง worktree อยู่แล้วหรือไม่? อาจเป็นเครื่องมือชื่อ `EnterWorktree`, `WorktreeCreate`, คำสั่ง `/worktree` หรือแฟล็ก `--worktree` ถ้ามี ให้ใช้มันแล้วข้ามไปขั้น 2

เครื่องมือเนทีฟจัดการตำแหน่งไดเรกทอรี การสร้าง branch และการล้างให้อัตโนมัติ การใช้ `git worktree add` ทั้งที่มีเครื่องมือเนทีฟ จะสร้างสถานะผีที่ harness มองไม่เห็นและจัดการไม่ได้

ไปขั้น 1b เฉพาะเมื่อไม่มีเครื่องมือ worktree เนทีฟ

### 1b. ทางสำรองด้วย Git Worktree

**ใช้เฉพาะเมื่อขั้น 1a ไม่เข้าเงื่อนไข** - ไม่มีเครื่องมือ worktree เนทีฟ ให้สร้าง worktree เองด้วย git

#### การเลือกไดเรกทอรี

ทำตามลำดับความสำคัญนี้ ความต้องการที่ผู้ใช้ระบุชัดเจนชนะสถานะของระบบไฟล์ที่สังเกตได้เสมอ

1. **ตรวจคำสั่งของคุณว่ามีไดเรกทอรี worktree ที่ประกาศไว้หรือไม่** ถ้าผู้ใช้ระบุแล้ว ใช้เลยโดยไม่ต้องถาม

2. **ตรวจว่ามีไดเรกทอรี worktree ในโปรเจกต์อยู่แล้วหรือไม่:**
   ```bash
   ls -d .worktrees 2>/dev/null     # แนะนำ (ซ่อน)
   ls -d worktrees 2>/dev/null      # ทางเลือก
   ```
   ถ้าเจอ ให้ใช้ ถ้ามีทั้งคู่ `.worktrees` ชนะ

3. **ถ้าไม่มีแนวทางอื่น** ใช้ `.worktrees/` ที่รากโปรเจกต์เป็นค่าตั้งต้น

#### ตรวจความปลอดภัย (เฉพาะไดเรกทอรีในโปรเจกต์)

**ต้องตรวจว่าไดเรกทอรีถูก ignore ก่อนสร้าง worktree:**

```bash
git check-ignore -q .worktrees 2>/dev/null || git check-ignore -q worktrees 2>/dev/null
```

**ถ้ายังไม่ถูก ignore:** เพิ่มเข้า .gitignore, commit การเปลี่ยนแปลง แล้วค่อยดำเนินการ

**ทำไมสำคัญ:** ป้องกันการ commit เนื้อหาของ worktree เข้า repository โดยไม่ตั้งใจ

#### สร้าง Worktree

```bash
# กำหนดพาธตามตำแหน่งที่เลือก
path="$LOCATION/$BRANCH_NAME"

git worktree add "$path" -b "$BRANCH_NAME"
cd "$path"
```

**ทางสำรองเมื่อติด sandbox:** ถ้า `git worktree add` ล้มเหลวด้วยข้อผิดพลาดสิทธิ์ (sandbox ปฏิเสธ) ให้บอกผู้ใช้ว่า sandbox บล็อกการสร้าง worktree และคุณจะทำงานในไดเรกทอรีปัจจุบันแทน จากนั้นรันการตั้งค่าและเทสต์ตั้งต้นในที่เดิม

## ขั้น 2: ตั้งค่าโปรเจกต์

ตรวจจับและรันการตั้งค่าที่เหมาะสมโดยอัตโนมัติ:

```bash
# Node.js
if [ -f package.json ]; then npm install; fi

# Rust
if [ -f Cargo.toml ]; then cargo build; fi

# Python
if [ -f requirements.txt ]; then pip install -r requirements.txt; fi
if [ -f pyproject.toml ]; then poetry install; fi

# Go
if [ -f go.mod ]; then go mod download; fi
```

## ขั้น 3: ตรวจสอบว่าสถานะตั้งต้นสะอาด

รันเทสต์เพื่อให้แน่ใจว่า workspace เริ่มต้นสะอาด:

```bash
# ใช้คำสั่งที่เหมาะกับโปรเจกต์
npm test / cargo test / pytest / go test ./...
```

**ถ้าเทสต์ล้มเหลว:** รายงานความล้มเหลว ถามว่าจะไปต่อหรือสืบสวน

**ถ้าเทสต์ผ่าน:** รายงานว่าพร้อม

### รายงาน

```
Worktree พร้อมที่ <full-path>
เทสต์ผ่าน (<N> เทสต์, ล้มเหลว 0)
พร้อมทำ <feature-name>
```

## ตารางอ้างอิงด่วน

| สถานการณ์ | การกระทำ |
|-----------|--------|
| อยู่ใน linked worktree แล้ว | ข้ามการสร้าง (ขั้น 0) |
| อยู่ใน submodule | ปฏิบัติเหมือน repo ปกติ (ตัวป้องกันขั้น 0) |
| มีเครื่องมือ worktree เนทีฟ | ใช้มัน (ขั้น 1a) |
| ไม่มีเครื่องมือเนทีฟ | ทางสำรอง git worktree (ขั้น 1b) |
| มี `.worktrees/` | ใช้มัน (ตรวจว่าถูก ignore) |
| มี `worktrees/` | ใช้มัน (ตรวจว่าถูก ignore) |
| มีทั้งสอง | ใช้ `.worktrees/` |
| ไม่มีทั้งสอง | ตรวจไฟล์คำสั่ง แล้วใช้ `.worktrees/` เป็นค่าตั้งต้น |
| ไดเรกทอรียังไม่ถูก ignore | เพิ่มใน .gitignore + commit |
| ข้อผิดพลาดสิทธิ์ตอนสร้าง | ทางสำรอง sandbox ทำงานในที่เดิม |
| เทสต์ล้มเหลวตอนตรวจสถานะตั้งต้น | รายงานความล้มเหลว + ถาม |
| ไม่มี package.json/Cargo.toml | ข้ามการติดตั้ง dependency |

## ข้ออ้างที่พบบ่อย

| ข้ออ้าง | ความจริง |
|--------|---------|
| "ชัดอยู่แล้วว่าไม่ได้อยู่ใน worktree ไม่ต้องตรวจ" | รันขั้น 0 การแยกที่ harness สร้างและ submodule หลอกสายตาได้ทั้งคู่ คำสั่งตรวจจับตัดสินได้ |
| "`git worktree add` เร็วกว่าไปหาเครื่องมือเนทีฟ" | เครื่องมือเนทีฟ (เช่น `EnterWorktree`) ดูแลตำแหน่ง การสร้าง branch และการล้าง การข้ามมันเป็นความผิดพลาดอันดับ 1 - สร้างสถานะผีที่ harness มองไม่เห็นและจัดการไม่ได้ |
| "ไดเรกทอรี worktree น่าจะถูก ignore อยู่แล้ว" | รัน `git check-ignore` ไดเรกทอรี worktree ที่ไม่ถูก ignore จะ commit ทั้งต้นไม้เข้า repo |
| "ชื่อไดเรกทอรีอะไรก็ได้" | คำสั่งที่ชัดเจนชนะไดเรกทอรีในโปรเจกต์ที่มีอยู่ ซึ่งชนะค่าตั้งต้น `.worktrees/` |
| "workspace ใหม่ เทสต์ตั้งต้นรอก่อนได้" | สถานะตั้งต้นที่สกปรกทำให้ความล้มเหลวทุกครั้งหลังจากนั้นคลุมเครือ รันเทสต์ตอนนี้ การไปต่อทั้งที่ล้มเหลวเป็นการตัดสินใจของ human partner |
