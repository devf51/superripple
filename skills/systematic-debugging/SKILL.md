# การดีบักอย่างเป็นระบบ

## ภาพรวม

**หลักการ:** หาสาเหตุราก "ก่อน" ลองแก้เสมอ การแก้ที่อาการคือความล้มเหลว

**ละเมิดตัวอักษรของกระบวนการนี้ คือละเมิดเจตนารมณ์ของการดีบัก**

## กฎเหล็ก

```
ห้ามแก้ จนกว่าจะสืบสวนหาสาเหตุรากก่อน
```

ถ้ายังไม่จบเฟส 1 คุณเสนอวิธีแก้ไม่ได้

## เมื่อไหร่ควรใช้

ใช้กับปัญหาทางเทคนิค "ทุกชนิด":
- เทสต์ล้มเหลว
- บั๊กใน production
- พฤติกรรมที่ไม่คาดคิด
- ปัญหาประสิทธิภาพ
- build ล้มเหลว
- ปัญหาการเชื่อมต่อ

**ใช้ "โดยเฉพาะ" เมื่อ:**
- ถูกกดดันเรื่องเวลา (เหตุฉุกเฉินทำให้อยากเดา)
- "แก้เร็วๆ แค่จุดเดียว" ดูชัดเจน
- ลองแก้มาหลายครั้งแล้ว
- วิธีแก้ครั้งก่อนไม่ได้ผล
- ยังไม่เข้าใจปัญหาอย่างถ่องแท้

**ห้ามข้ามเมื่อ:**
- ปัญหาดูง่าย (บั๊กง่ายๆ ก็มีสาเหตุราก)
- รีบ (การรีบรับประกันว่าต้องทำใหม่)
- หัวหน้าอยากให้แก้เดี๋ยวนี้ (ทำเป็นระบบเร็วกว่าการวุ่นวายไปมา)

## สี่เฟส

คุณ "ต้อง" จบแต่ละเฟสก่อนไปเฟสถัดไป

### เฟส 1: สืบสวนสาเหตุราก

**ก่อนจะลองแก้ "อะไรก็ตาม":**

1. **อ่านข้อความ error อย่างละเอียด**
   - อย่าข้าม error หรือ warning
   - มันมักมีคำตอบที่แน่นอนอยู่
   - อ่าน stack trace ให้ครบ
   - จดเลขบรรทัด พาธไฟล์ รหัส error

2. **ทำให้เกิดซ้ำได้สม่ำเสมอ**
   - กระตุ้นให้เกิดได้อย่างเชื่อถือได้ไหม?
   - ขั้นตอนที่แน่นอนคืออะไร?
   - เกิดทุกครั้งไหม?
   - ถ้าทำซ้ำไม่ได้ → รวบรวมข้อมูลเพิ่ม อย่าเดา

3. **ตรวจการเปลี่ยนแปลงล่าสุด**
   - อะไรเปลี่ยนที่อาจทำให้เกิดเรื่องนี้?
   - Git diff, commit ล่าสุด
   - dependency ใหม่, การเปลี่ยน config
   - ความต่างของสภาพแวดล้อม

4. **รวบรวมหลักฐานในระบบหลาย component**

   **เมื่อระบบมีหลาย component (CI → build → signing, API → service → database):**

   **ก่อนเสนอวิธีแก้ ให้เพิ่มเครื่องมือวินิจฉัย:**
   ```
   สำหรับ "แต่ละ" ขอบเขตของ component:
     - log ข้อมูลที่เข้า component
     - log ข้อมูลที่ออกจาก component
     - ตรวจว่า environment/config ถูกส่งต่อ
     - ตรวจสถานะในแต่ละชั้น

   รันหนึ่งครั้งเพื่อรวบรวมหลักฐานที่แสดงว่าพังที่ "ไหน"
   จากนั้นวิเคราะห์หลักฐานเพื่อระบุ component ที่ล้มเหลว
   จากนั้นสืบสวน component นั้นโดยเฉพาะ
   ```

   **ตัวอย่าง (ระบบหลายชั้น):**
   ```bash
   # ชั้น 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: $([ -n "${IDENTITY:-}" ] && echo SET || echo UNSET)"

   # ชั้น 2: สคริปต์ build
   echo "=== Env vars in build script: ==="
   printenv IDENTITY >/dev/null 2>&1 && echo "IDENTITY in environment" || echo "IDENTITY not in environment"

   # ชั้น 3: สคริปต์ signing
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # ชั้น 4: การ signing จริง
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **สิ่งนี้เผยให้เห็น:** ชั้นไหนล้มเหลว (secrets → workflow ✓, workflow → build ✗)

5. **ไล่ตามการไหลของข้อมูล**

   **เมื่อ error อยู่ลึกใน call stack:**

   ดู `root-cause-tracing.md` ในไดเรกทอรีนี้สำหรับเทคนิคการไล่ย้อนกลับฉบับเต็ม

   **ฉบับย่อ:**
   - ค่าที่ผิดมาจากไหน?
   - อะไรเรียกด้วยค่าที่ผิดนี้?
   - ไล่ขึ้นไปเรื่อยๆ จนเจอต้นตอ
   - แก้ที่ต้นตอ ไม่ใช่ที่อาการ

### เฟส 2: วิเคราะห์รูปแบบ

**หารูปแบบก่อนแก้:**

1. **หาตัวอย่างที่ทำงานได้**
   - หาโค้ดที่คล้ายกันและทำงานได้ในโค้ดเบสเดียวกัน
   - อะไรที่ทำงานได้และคล้ายกับสิ่งที่พัง?

2. **เทียบกับตัวอ้างอิง**
   - ถ้ากำลังทำตามรูปแบบ ให้อ่านการเขียนอ้างอิง "ให้ครบ"
   - อย่าอ่านผ่านๆ - อ่านทุกบรรทัด
   - เข้าใจรูปแบบอย่างสมบูรณ์ก่อนนำไปใช้

3. **ระบุความต่าง**
   - อะไรต่างระหว่างอันที่ทำงานกับอันที่พัง?
   - ระบุทุกความต่าง แม้เล็กน้อย
   - อย่าสมมติว่า "นั่นไม่น่ามีผล"

4. **เข้าใจ dependency**
   - มันต้องใช้ component อื่นอะไรบ้าง?
   - การตั้งค่า config สภาพแวดล้อมอะไร?
   - มันสมมติอะไรไว้?

### เฟส 3: สมมติฐานและการทดสอบ

**วิธีวิทยาศาสตร์:**

1. **ตั้งสมมติฐานเดียว**
   - บอกชัดๆ: "ผมคิดว่า X คือสาเหตุราก เพราะ Y"
   - เขียนลงไป
   - เจาะจง ไม่คลุมเครือ

2. **ทดสอบให้น้อยที่สุด**
   - ทำการเปลี่ยนแปลงที่ "เล็กที่สุด" เพื่อทดสอบสมมติฐาน
   - ทีละตัวแปร
   - อย่าแก้หลายอย่างพร้อมกัน

3. **ตรวจสอบก่อนไปต่อ**
   - ได้ผลไหม? ได้ → เฟส 4
   - ไม่ได้ผล? ตั้งสมมติฐาน "ใหม่"
   - อย่าเพิ่มการแก้ซ้อนทับ

4. **เมื่อไม่รู้**
   - พูดว่า "ผมไม่เข้าใจ X"
   - อย่าแกล้งว่ารู้
   - ขอความช่วยเหลือ
   - ค้นคว้าเพิ่ม

### เฟส 4: ลงมือแก้

**แก้สาเหตุราก ไม่ใช่อาการ:**

1. **สร้างเทสต์เคสที่ล้มเหลว**
   - การทำซ้ำที่ง่ายที่สุด
   - เทสต์อัตโนมัติถ้าทำได้
   - สคริปต์เทสต์แบบใช้ครั้งเดียวถ้าไม่มี framework
   - "ต้อง" มีก่อนแก้
   - ใช้ skill `superripple:test-driven-development` เพื่อเขียนเทสต์ที่ล้มเหลวอย่างถูกต้อง

2. **แก้ทีละจุด**
   - จัดการสาเหตุรากที่ระบุแล้ว
   - เปลี่ยน "ทีละอย่าง"
   - ห้าม "ไหนๆ ก็อยู่นี่แล้ว" ปรับปรุงอย่างอื่น
   - ห้ามรวม refactor เข้ามา

3. **ตรวจสอบการแก้**
   - เทสต์ผ่านแล้วไหม?
   - ไม่มีเทสต์อื่นพังใช่ไหม?
   - ปัญหาแก้ได้จริงไหม?
   - ใช้ skill `superripple:verification-before-completion` ก่อนอ้างความสำเร็จ

4. **ถ้าแก้ไม่ได้ผล**
   - หยุด
   - นับ: ลองแก้มากี่ครั้งแล้ว?
   - ถ้า < 3: กลับไปเฟส 1 วิเคราะห์ใหม่ด้วยข้อมูลใหม่
   - **ถ้า ≥ 3: หยุดและตั้งคำถามกับสถาปัตยกรรม (ข้อ 5 ด้านล่าง)**
   - ห้ามลองแก้ครั้งที่ 4 โดยไม่คุยเรื่องสถาปัตยกรรม

5. **ถ้าแก้ 3+ ครั้งไม่สำเร็จ: ตั้งคำถามกับสถาปัตยกรรม**

   **รูปแบบที่ชี้ถึงปัญหาสถาปัตยกรรม:**
   - แต่ละการแก้เผยสถานะร่วม/การเชื่อมโยง/ปัญหาใหม่ในที่อื่น
   - การแก้ต้องการ "refactor ครั้งใหญ่" จึงทำได้
   - แต่ละการแก้สร้างอาการใหม่ที่อื่น

   **หยุดและตั้งคำถามกับพื้นฐาน:**
   - รูปแบบนี้ถูกต้องในระดับพื้นฐานไหม?
   - เรา "ยึดมันไว้เพราะแรงเฉื่อยล้วนๆ" หรือเปล่า?
   - ควร refactor สถาปัตยกรรม หรือแก้อาการต่อไป?

   **คุยกับ human partner ก่อนลองแก้เพิ่ม**

   นี่ไม่ใช่สมมติฐานที่ผิด - นี่คือสถาปัตยกรรมที่ผิด

## สัญญาณเตือน - หยุดและทำตามกระบวนการ

ถ้าจับได้ว่าคิดว่า:
- "แก้เร็วๆ ไปก่อน ค่อยสืบสวนทีหลัง"
- "ลองเปลี่ยน X ดูว่าได้ผลไหม"
- "เพิ่มหลายการเปลี่ยนแปลงแล้วรันเทสต์"
- "ข้ามเทสต์ ผมตรวจเองด้วยมือ"
- "น่าจะเป็น X ขอแก้อันนั้น"
- "ผมยังไม่เข้าใจทั้งหมดแต่อันนี้อาจใช้ได้"
- "รูปแบบบอก X แต่ผมจะปรับให้ต่างออกไป"
- "ปัญหาหลักๆ คือ: [ลิสต์วิธีแก้โดยไม่สืบสวน]"
- เสนอวิธีแก้ก่อนไล่การไหลของข้อมูล
- **"ขอลองแก้อีกครั้ง" (ทั้งที่ลองมาแล้ว 2+ ครั้ง)**
- **แต่ละการแก้เผยปัญหาใหม่ในที่อื่น**

**ทั้งหมดนี้หมายความว่า: หยุด กลับไปเฟส 1**

**ถ้าแก้ 3+ ครั้งไม่สำเร็จ:** ตั้งคำถามกับสถาปัตยกรรม (ดูเฟส 4.5)

## สัญญาณจาก human partner ว่าคุณทำผิด

**สังเกตการชี้นำเหล่านี้:**
- "ไม่ได้เกิดขึ้นเหรอ?" - คุณสมมติโดยไม่ตรวจสอบ
- "มันจะแสดงให้เราเห็นไหมว่า...?" - คุณควรเพิ่มการรวบรวมหลักฐาน
- "เลิกเดา" - คุณเสนอวิธีแก้โดยไม่เข้าใจ
- "คิดให้ลึกสุดๆ" - ตั้งคำถามกับพื้นฐาน ไม่ใช่แค่อาการ
- "เราติดแล้วเหรอ?" (หงุดหงิด) - แนวทางของคุณใช้ไม่ได้

**เมื่อเห็นสิ่งเหล่านี้:** หยุด กลับไปเฟส 1

## ข้ออ้างที่พบบ่อย

| ข้ออ้าง | ความจริง |
|--------|---------|
| "ปัญหาง่าย ไม่ต้องมีกระบวนการ" | ปัญหาง่ายก็มีสาเหตุราก กระบวนการเร็วสำหรับบั๊กง่าย |
| "ฉุกเฉิน ไม่มีเวลาทำตามกระบวนการ" | การดีบักอย่างเป็นระบบ "เร็วกว่า" การเดาและวุ่นวายไปมา |
| "ลองอันนี้ก่อน แล้วค่อยสืบสวน" | การแก้ครั้งแรกวางรูปแบบ ทำให้ถูกตั้งแต่แรก |
| "จะเขียนเทสต์หลังยืนยันว่าแก้ได้" | การแก้ที่ไม่มีเทสต์ไม่ยั่งยืน เทสต์ก่อนพิสูจน์ได้ |
| "แก้หลายอย่างพร้อมกันประหยัดเวลา" | แยกไม่ได้ว่าอะไรได้ผล ก่อบั๊กใหม่ |
| "ตัวอ้างอิงยาวเกิน ขอปรับรูปแบบเอง" | เข้าใจบางส่วนรับประกันบั๊ก อ่านให้ครบ |
| "เห็นปัญหาแล้ว ขอแก้เลย" | เห็นอาการ ≠ เข้าใจสาเหตุราก |
| "ขอลองแก้อีกครั้ง" (หลังล้มเหลว 2+ ครั้ง) | ล้มเหลว 3+ ครั้ง = ปัญหาสถาปัตยกรรม ตั้งคำถามกับรูปแบบ อย่าแก้ซ้ำ |

## ตารางอ้างอิงด่วน

| เฟส | กิจกรรมหลัก | เกณฑ์สำเร็จ |
|-------|---------------|------------------|
| **1. สาเหตุราก** | อ่าน error, ทำซ้ำ, ตรวจการเปลี่ยนแปลง, รวบรวมหลักฐาน | เข้าใจ "อะไร" และ "ทำไม" |
| **2. รูปแบบ** | หาตัวอย่างที่ทำงานได้, เปรียบเทียบ | ระบุความต่างได้ |
| **3. สมมติฐาน** | ตั้งทฤษฎี, ทดสอบให้น้อยที่สุด | ยืนยันหรือได้สมมติฐานใหม่ |
| **4. ลงมือแก้** | สร้างเทสต์, แก้, ตรวจสอบ | แก้บั๊กได้ เทสต์ผ่าน |

## เมื่อกระบวนการเผยว่า "ไม่มีสาเหตุราก"

ถ้าการสืบสวนอย่างเป็นระบบเผยว่าปัญหาเป็นเรื่องสภาพแวดล้อม ขึ้นกับจังหวะเวลา หรือมาจากภายนอกจริงๆ:

1. คุณจบกระบวนการแล้ว
2. บันทึกสิ่งที่สืบสวน
3. ทำการจัดการที่เหมาะสม (retry, timeout, ข้อความ error)
4. เพิ่ม monitoring/logging สำหรับการสืบสวนในอนาคต

**แต่:** 95% ของกรณี "ไม่มีสาเหตุราก" คือการสืบสวนที่ยังไม่ครบ

## เทคนิคสนับสนุน

เทคนิคเหล่านี้เป็นส่วนของการดีบักอย่างเป็นระบบและอยู่ในไดเรกทอรีนี้:

- **`root-cause-tracing.md`** - ไล่บั๊กย้อนผ่าน call stack เพื่อหาตัวกระตุ้นเดิม
- **`defense-in-depth.md`** - เพิ่มการตรวจสอบหลายชั้นหลังพบสาเหตุราก
- **`condition-based-waiting.md`** - แทนที่ timeout ตามอำเภอใจด้วยการ poll เงื่อนไข
