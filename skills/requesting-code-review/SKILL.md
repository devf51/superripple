# การขอ Code Review

ส่ง subagent ผู้รีวิวโค้ดไปจับปัญหาก่อนที่มันจะลุกลาม ผู้รีวิวจะได้บริบทที่คัดมาอย่างตรงจุดเพื่อประเมิน ไม่ใช่ประวัติของ session คุณ

**หลักการ:** รีวิวเร็ว รีวิวบ่อย

## เมื่อไหร่ต้องขอรีวิว

**ต้องทำ:**
- หลังจบแต่ละงานใน subagent-driven development
- หลังทำฟีเจอร์ใหญ่เสร็จ
- ก่อน merge เข้า main

**ไม่บังคับแต่มีประโยชน์:**
- ตอนติดขัด (ได้มุมมองใหม่)
- ก่อน refactor (ตรวจสถานะตั้งต้น)
- หลังแก้บั๊กที่ซับซ้อน

## วิธีขอ

**1. หา git SHA:**
```bash
BASE_SHA=$(git rev-parse HEAD~1)  # หรือ: git merge-base origin/main HEAD
HEAD_SHA=$(git rev-parse HEAD)
```

**2. ส่ง subagent ผู้รีวิวโค้ด:**

ส่ง subagent ชนิด `general-purpose` โดยกรอกเทมเพลตที่ [code-reviewer.md](code-reviewer.md)

**ตัวแปรที่ต้องกรอก:**
- `{DESCRIPTION}` - สรุปสั้นๆ ว่าสร้างอะไร
- `{PLAN_OR_REQUIREMENTS}` - งานนี้ควรทำอะไร
- `{BASE_SHA}` - commit เริ่มต้น
- `{HEAD_SHA}` - commit สิ้นสุด

**3. ลงมือแก้ตามผลรีวิว:**
- แก้ปัญหา Critical ทันที
- แก้ปัญหา Important ก่อนไปต่อ
- จด Minor ไว้ทำทีหลัง
- โต้กลับถ้าผู้รีวิวผิด (พร้อมเหตุผล)

## ตัวอย่าง

```
[เพิ่งทำ Task 2 เสร็จ: เพิ่มฟังก์ชัน verification]

คุณ: ขอรีวิวโค้ดก่อนไปต่อ

BASE_SHA=$(git log --oneline | grep "Task 1" | head -1 | cut -d' ' -f1)
HEAD_SHA=$(git rev-parse HEAD)

[ส่ง subagent ผู้รีวิวโค้ด]
  DESCRIPTION: เพิ่ม verifyIndex() และ repairIndex() รองรับปัญหา 4 ประเภท
  PLAN_OR_REQUIREMENTS: Task 2 จาก docs/superpowers/plans/deployment-plan.md
  BASE_SHA: a7981ec
  HEAD_SHA: 3df7661

[subagent ตอบกลับ]:
  จุดแข็ง: สถาปัตยกรรมสะอาด มีเทสต์จริง
  ปัญหา:
    Important: ไม่มีตัวบอกความคืบหน้า
    Minor: ใช้เลขมายากล (100) เป็นช่วงรายงาน
  สรุป: ไปต่อได้

คุณ: [แก้ตัวบอกความคืบหน้า]
[ไปต่อ Task 3]
```

## ข้ออ้างที่พบบ่อย

| ข้ออ้าง | ความจริง |
|--------|---------|
| "ขอดู diff เองแทนการส่งผู้รีวิว" | คุณเป็นผู้ประสานงาน การรีวิว diff เองจะกิน context window ที่ต้องใช้ขับงานต่อ ให้ส่ง subagent ผู้รีวิว diff และการประเมินจะอยู่ใน context ของมัน และส่งกลับมาเฉพาะข้อค้นพบ |
| "ผู้รีวิวต้องรู้ประวัติ session ทั้งหมดถึงจะเข้าใจการเปลี่ยนแปลง" | ให้บริบทที่คัดมาอย่างตรงจุด ห้ามให้ประวัติ session เพื่อให้ผู้รีวิวโฟกัสที่ตัวงาน ไม่ใช่กระบวนการคิดของคุณ |

## สัญญาณเตือน

**ห้ามเด็ดขาด:**
- ข้ามการรีวิวเพราะ "มันง่าย"
- เมินปัญหา Critical
- ไปต่อทั้งที่ปัญหา Important ยังไม่ถูกแก้
- เถียงกับข้อเสนอแนะทางเทคนิคที่ถูกต้อง

**ถ้าผู้รีวิวผิด:**
- โต้ด้วยเหตุผลทางเทคนิค
- แสดงโค้ด/เทสต์ที่พิสูจน์ว่าทำงานได้
- ขอให้ชี้แจง
