# การเขียนแผน

## ภาพรวม

เขียนแผนการพัฒนาสำหรับวิศวกรที่ไม่เคยเห็นโค้ดเบสนี้หรือ spec นี้ สมมติว่าพวกเขาเขียนโค้ดตามสำนวนของภาษาในโปรเจกต์ได้ เมื่อรู้ interface ที่แน่นอนและเทสต์ที่แน่นอน และจะเลือกทางที่สมเหตุสมผลเมื่อแผนเปิดทางไว้ สิ่งที่พวกเขาไม่มีทางรู้คือสิ่งที่คุณตัดสินใจ: ไฟล์ไหน ชื่อและ signature อะไร ค่าอะไรจาก spec เทสต์ไหนพิสูจน์แต่ละงาน ให้เขียนสิ่งเหล่านั้นลงไป ให้แผนทั้งหมดเป็นงานย่อยขนาดพอดีคำ DRY YAGNI TDD commit บ่อยๆ

**ประกาศตอนเริ่ม:** "ผมใช้ skill writing-plans เพื่อสร้างแผนการพัฒนา"

**บริบท:** ถ้าทำงานใน worktree แยก มันควรถูกสร้างผ่าน skill `super-ripple:using-git-worktrees` ตอนลงมือ

**บันทึกแผนที่:** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- (ความต้องการของผู้ใช้เรื่องตำแหน่งแผนชนะค่าตั้งต้นนี้)

## ตรวจขอบเขต

ถ้า spec ครอบคลุมระบบย่อยที่เป็นอิสระหลายตัว มันควรถูกแตกเป็น spec ย่อยของโปรเจกต์ระหว่าง brainstorming แล้ว ถ้ายังไม่ได้แตก ให้เสนอให้แยกเป็นหลายแผน — หนึ่งแผนต่อหนึ่งระบบย่อย แต่ละแผนควรได้ซอฟต์แวร์ที่ทำงานและทดสอบได้ในตัวเอง

## โครงสร้างไฟล์

ก่อนกำหนดงาน ให้วางแผนว่าไฟล์ไหนจะถูกสร้างหรือแก้ และแต่ละไฟล์รับผิดชอบอะไร นี่คือจุดที่การตัดสินใจเรื่องการแยกส่วนถูกล็อก

- ออกแบบหน่วยที่มีขอบเขตชัดและ interface ที่นิยามดี แต่ละไฟล์ควรมีความรับผิดชอบเดียวที่ชัดเจน
- คุณให้เหตุผลกับโค้ดที่ถือใน context ได้ครั้งเดียวดีที่สุด และการแก้ของคุณน่าเชื่อถือกว่าเมื่อไฟล์โฟกัส ควรเลือกไฟล์เล็กที่โฟกัสแทนไฟล์ใหญ่ที่ทำหลายอย่าง
- ไฟล์ที่เปลี่ยนด้วยกันควรอยู่ด้วยกัน แยกตามความรับผิดชอบ ไม่ใช่ตามชั้นทางเทคนิค
- ในโค้ดเบสที่มีอยู่ ให้ทำตามแบบแผนที่ตั้งไว้ ถ้าโค้ดเบสใช้ไฟล์ใหญ่ อย่าจัดโครงสร้างใหม่ตามอำเภอใจ - แต่ถ้าไฟล์ที่คุณแก้ใหญ่จนเทอะทะ การใส่การแยกไฟล์ในแผนก็สมเหตุสมผล

โครงสร้างนี้เป็นฐานของการแตกงาน แต่ละงานควรให้การเปลี่ยนแปลงที่ครบในตัวและมีความหมายโดยลำพัง

## การกำหนดขนาดงานให้พอดี

งานคือหน่วยที่เล็กที่สุดที่มีวงจรเทสต์ของตัวเองและคุ้มกับด่านของผู้รีวิวหน้าใหม่ เมื่อลากเส้นแบ่งงาน: รวมขั้นตั้งค่า, configuration, scaffolding และเอกสารเข้ากับงานที่ผลลัพธ์ต้องใช้มัน แยกเฉพาะที่ผู้รีวิวอาจปฏิเสธงานหนึ่งแต่อนุมัติงานข้างเคียงได้อย่างมีความหมาย แต่ละงานจบด้วยผลลัพธ์ที่ทดสอบได้อย่างอิสระ

## ความละเอียดของขั้นตอน

**แต่ละขั้นคือหนึ่งการกระทำที่มีผลตรวจสอบได้:**
- "เขียนเทสต์ที่ล้มเหลว" - ขั้นหนึ่ง
- "รันให้แน่ใจว่าล้มเหลว" - ขั้นหนึ่ง
- "เขียนโค้ดน้อยที่สุดให้เทสต์ผ่าน" - ขั้นหนึ่ง
- "รันเทสต์ให้แน่ใจว่าผ่าน" - ขั้นหนึ่ง
- "Commit" - ขั้นหนึ่ง

## หัวเอกสารแผน

**ทุกแผน "ต้อง" เริ่มด้วยหัวนี้:**

```markdown
# แผนการพัฒนา [ชื่อฟีเจอร์]

> **สำหรับ agent ผู้ทำงาน:** SUB-SKILL ที่ต้องใช้: ใช้ super-ripple:subagent-driven-development (แนะนำ) หรือ super-ripple:executing-plans เพื่อทำแผนนี้ทีละงาน ขั้นตอนใช้ไวยากรณ์ checkbox (`- [ ]`) เพื่อติดตาม

**เป้าหมาย:** [ประโยคเดียวที่บอกว่าสร้างอะไร]

**สถาปัตยกรรม:** [2-3 ประโยคเกี่ยวกับแนวทาง]

**Tech Stack:** [เทคโนโลยี/ไลบรารีหลัก]

**Spec:** [พาธของ spec/design doc ที่แผนนี้ทำตาม — แผนอ้างเหตุผลจาก spec
ดังนั้น spec ต้องไปด้วยกัน ผู้ทำงานอ่านทั้งคู่]

## ข้อจำกัดทั่วไป

[ข้อกำหนดระดับโปรเจกต์ของ spec — เวอร์ชันขั้นต่ำ, ข้อจำกัดของ dependency,
กฎการตั้งชื่อและข้อความ, ข้อกำหนดแพลตฟอร์ม — บรรทัดละข้อ โดยคัดลอกค่าที่
แน่นอนจาก spec ตรงตัว ข้อกำหนดของทุกงานรวมส่วนนี้โดยปริยาย]

## จุดที่ต้องรีวิว

[อินพุตห้าประเภทหรือโหมดล้มเหลวที่ spec บ่งชี้ แต่ไม่มีเทสต์ของงานใด
ครอบคลุม และมีแนวโน้มสูงสุดที่จะกัดผู้ใช้ซอฟต์แวร์นี้ — บรรทัดละข้อ
ระบุอินพุตหรือเงื่อนไข และพฤติกรรมที่คนทั่วไปคาดหวัง เรียงจากที่น่าจะเกิด
มากที่สุด spec เป็นเอกสารวิสัยทัศน์: บอกว่าซอฟต์แวร์ต้องทำอะไร ไม่ใช่ทุกสิ่ง
ที่มันจะเจอ และการที่ spec เงียบเรื่องอินพุตหนึ่งไม่ได้อนุญาตให้อินพุตนั้น
ทำโปรแกรมพัง เขียนรายการที่นี่ครั้งเดียว โดยมี spec อยู่ตรงหน้า จากนั้น
ในแต่ละบรรทัด เพิ่มเทสต์ที่ตรึงมันลงในงานที่เป็นเจ้าของโค้ดนั้น ด้วยรูปแบบ
ขั้นตอนของงานนั้นเอง]

---
```

## โครงสร้างงาน

````markdown
### งานที่ N: [ชื่อ Component]

**ไฟล์:**
- สร้าง: `exact/path/to/file.py`
- แก้: `exact/path/to/existing.py:123-145`
- เทสต์: `tests/exact/path/to/test.py`

**Interfaces:**
- ใช้: [สิ่งที่งานนี้ใช้จากงานก่อนหน้า — signature ที่แน่นอน]
- ผลิต: [สิ่งที่งานหลังๆ พึ่งพา — ชื่อฟังก์ชัน ชนิดพารามิเตอร์
  และชนิดค่าคืนที่แน่นอน ผู้ทำงานเห็นเฉพาะงานของตัวเอง
  บล็อกนี้คือวิธีที่พวกเขารู้ชื่อและชนิดที่งานข้างเคียงใช้]

- [ ] **ขั้น 1: เขียนเทสต์ที่ล้มเหลว**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **ขั้น 2: รันเทสต์เพื่อยืนยันว่าล้มเหลว**

รัน: `pytest tests/path/test.py::test_name -v`
คาดหวัง: FAIL พร้อมข้อความ "function not defined"

- [ ] **ขั้น 3: เขียน `function(input: InputType) -> ResultType` ใน `exact/path/to/file.py`**

หนึ่งบรรทัดเกี่ยวกับแนวทางเมื่อ signature และเทสต์ยังเปิดให้เลือก
(เรียกไลบรารีตัวไหน ใช้โครงสร้างข้อมูลอะไร) บล็อกโค้ดใส่เฉพาะ
อัลกอริทึมที่ทั้งสองอย่างไม่ได้กำหนด

- [ ] **ขั้น 4: รันเทสต์เพื่อยืนยันว่าผ่าน**

รัน: `pytest tests/path/test.py::test_name -v`
คาดหวัง: PASS

- [ ] **ขั้น 5: Commit**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## สิ่งที่ขั้นตอนต้องมี

ขั้นตอนเสร็จเมื่อผู้ทำงานเขียนได้อย่างสมเหตุสมผลเพียงอย่างเดียวจากมัน นั่นคือข้อกำหนดทั้งหมด: ไม่กำกวม ไม่ใช่ครบถ้วน ขั้นตอนแต่ละชนิดมีสิ่งที่ทำให้ไม่กำกวมและไม่เกินนั้น:

- **ขั้นเทสต์:** ชื่อเทสต์และ assertion ของมัน เป็นโค้ด พร้อมค่าที่แน่นอนจาก spec
- **ขั้นโค้ด:** signature ที่แน่นอน (ชื่อ พารามิเตอร์ ชนิดค่าคืน) ไฟล์ที่มันอยู่ และค่าเฉพาะที่ spec กำหนด ผู้ทำงานเขียนตัวฟังก์ชันเอง ตัวฟังก์ชันปรากฏเฉพาะสำหรับอัลกอริทึมที่ signature และเทสต์ไม่ได้กำหนด หรือข้อความที่ spec กำหนดตายตัว
- **ขั้นตรวจสอบ:** คำสั่งที่จะรันและผลลัพธ์ที่หมายความว่าผ่าน
- **การอ้างถึงงานอื่น:** บล็อก Interfaces ของงานนั้นบอกว่าจะใช้อะไร แผนไม่ทำซ้ำโค้ดของงานนั้น

แผนคือชุดของการตัดสินใจที่ผู้ทำงานตัดสินเองไม่ได้ แผนที่ยาวกว่าโค้ดที่มันอธิบาย คือเขียนโค้ดแทนที่จะเป็นแผน บรรทัดที่ไม่ตัดสินอะไร ("TBD", "จัดการ edge case", "เพิ่ม validation ที่เหมาะสม", "เขียนเทสต์สำหรับข้างบน", ชนิดหรือฟังก์ชันที่ไม่มีงานใดนิยาม) คือความล้มเหลวด้านตรงข้าม และการรีวิวตัวเองจับได้ทั้งสองแบบ

## รีวิวตัวเอง

หลังเขียนแผนครบ ให้มอง spec ด้วยสายตาใหม่และตรวจแผนเทียบกับมัน นี่คือ checklist ที่คุณรันเอง — ไม่ใช่การส่ง subagent

**1. ครอบคลุม spec:** ไล่ดูแต่ละส่วน/ข้อกำหนดใน spec ชี้ได้ไหมว่างานไหนทำมัน? ระบุช่องว่างทั้งหมด

**2. สแกนขั้นตอน:** ทุกขั้นต้องให้ผู้ทำงานเขียนได้อย่างสมเหตุสมผลเพียงอย่างเดียว และห้ามมีขั้นใดบรรทุกเกินนั้น: บรรทัดที่ไม่ตัดสินอะไรคือช่องว่าง ตัวฟังก์ชันที่ signature และเทสต์กำหนดอยู่แล้วคือการถอดโค้ด แก้ทั้งสองแบบ

**3. ความสอดคล้องของชนิด:** ชนิด, signature ของ method และชื่อ property ที่ใช้ในงานหลังตรงกับที่นิยามในงานก่อนหรือไม่? ฟังก์ชันที่เรียก `clearLayers()` ในงานที่ 3 แต่ `clearFullLayers()` ในงานที่ 7 คือบั๊ก

**4. จุดที่ต้องรีวิว:** สำหรับแต่ละประเภทอินพุตหรือโหมดล้มเหลวที่ spec บ่งชี้ มีงานที่เทสต์ครอบคลุมไหม? ห้าข้อที่ไม่ได้ครอบคลุมและน่าจะกัดผู้ใช้มากที่สุดไปอยู่ในส่วนจุดที่ต้องรีวิว และแต่ละบรรทัดต้องเพิ่มเทสต์ในงานเจ้าของ ส่วนที่ว่างหมายความว่าตรวจแล้วไม่พบ ไม่ใช่ข้ามการตรวจ

**5. สัดส่วน:** เทียบความยาวของแผนกับ spec แผนที่ยาวกว่า spec หลายเท่าคือการถอดโค้ดของโปรแกรม ไม่ใช่แผน ถ้าบล็อกโค้ดเป็นส่วนใหญ่ของเอกสาร ให้เปลี่ยนตัวฟังก์ชันเป็น signature ชื่อเทสต์ และ assertion และตรวจว่าแต่ละขั้นยังไม่กำกวม

ถ้าพบปัญหา แก้ในนั้นเลย ไม่ต้องรีวิวซ้ำ — แก้แล้วไปต่อ ถ้าพบข้อกำหนดใน spec ที่ไม่มีงาน ให้เพิ่มงาน

## การส่งต่อเพื่อลงมือ

หลังบันทึกและรีวิวตัวเองแล้ว ให้ใส่ลิงก์ให้ human partner อ่าน ถ้าพวกเขาระบุวิธีลงมืออย่างชัดเจนไว้แล้ว ให้ขอให้พวกเขารีวิวแผนและยืนยันว่าตรงที่ต้องการ รอการรีวิวนั้นก่อนลงมือ แล้วใช้วิธีที่ระบุไว้ ถ้าไม่ ให้ขอให้พวกเขารีวิวแผนและเลือกวิธีลงมือก่อนลงมือ

**เมื่อยังไม่มีการระบุวิธีลงมือ:**

**"แผนเสร็จและบันทึกที่ `docs/superpowers/plans/<filename>.md` แล้ว กรุณารีวิวแผน คุณต้องการวิธีลงมือแบบไหน?**

- **Subagent-driven** - subagent หน้าใหม่ทำแต่ละงาน และผู้รีวิวหน้าใหม่ตรวจก่อนงานถัดไปเริ่ม แล้วรีวิวทั้ง branch ตอนท้าย ละเอียดที่สุด; ใช้ context ใหม่ต่อหนึ่งงานและต่อหนึ่งรีวิว
- **Native** - ผมทำทุกงานเองใน session นี้ ตามวิธีที่ harness นี้รันงาน แล้วผู้รีวิวหน้าใหม่หนึ่งคนบนโมเดลที่เก่งที่สุดตรวจทั้ง branch ถูกและเร็วที่สุด; ไม่มีการรีวิวอิสระจนถึงตอนท้าย ทำงานได้ดีกับโมเดลระดับกลางของ session เพราะแผนมีการออกแบบอยู่แล้ว

**สำหรับแผนนี้ผมแนะนำ <หนึ่งในสองแบบ> เพราะ <หนึ่งประโยคจากแผน: งานพึ่ง interface ของกันและกันแค่ไหน มีกี่งาน ความผิดพลาดที่ส่งออกไปแล้วมีราคาเท่าไร> แผนตรงกับที่คุณต้องการไหม และเราควรใช้วิธีไหน?"**

**เมื่อมีการระบุวิธีลงมือไว้แล้ว:**

**"แผนเสร็จและบันทึกที่ `docs/superpowers/plans/<filename>.md` แล้ว กรุณารีวิวแผน ตรงกับที่คุณต้องการไหม?"**
