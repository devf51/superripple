# การออกแบบ (Design)

ออกแบบ **วิธีทำ** จากสิ่งที่ spec บอกว่า **ต้องทำอะไรและทำไม** ผลคือเอกสารออกแบบหนึ่งฉบับที่ขั้นเขียนแผนอ่านแล้วแตกงานได้โดยไม่ต้องถามซ้ำ ไม่เขียนโค้ด ไม่ติดตั้งอะไร skill นี้ออกแบบระบบซอฟต์แวร์ ถ้างานไม่ใช่ซอฟต์แวร์ ไม่ต้องใช้ ไปขั้นเขียนแผนได้เลย

## เริ่มจากสิ่งที่มี

ไม่มีเอกสารขั้นก่อนหน้าก็เริ่มได้ ใช้อินพุตข้อแรกที่มี:

1. **spec** (ไฟล์ชื่อใดก็ได้ หรือที่ human partner ชี้) → อ่านทั้งไฟล์
2. **ข้อความที่พวกเขาเล่า** → ถามเฉพาะที่ขาดและเปลี่ยนการออกแบบ ไม่เกิน 3 ข้อ ทีละข้อ แต่ละข้อมีคำตอบที่คุณแนะนำและเหตุผลสั้นๆ ให้ตอบ "ใช่" คำเดียวได้ เรื่องเล็ก ตัดสินเองแล้วจดเป็นสมมติฐานในเอกสาร
3. **โค้ดที่มีอยู่** → อ่านโครงสร้างจริง ใช้ภาษา framework และเวอร์ชันที่โปรเจกต์ใช้ ไม่เปลี่ยนโดยไม่ถาม

ไม่มี spec ไม่ใช่เหตุให้หยุดหรือส่งกลับไปขั้นก่อน ถ้าเป้าหมายยังไม่ชัดจนคำตอบเปลี่ยนการออกแบบทั้งหมด ถามข้อเดียวที่ชัดที่สุด แล้วไปต่อ

## ผลลัพธ์

เอกสารเดียว ค่าเริ่มต้น `docs/design/<topic>-design.md` และ commit ถ้าเป็น repo ซอฟต์แวร์ ถ้า human partner หรือโปรเจกต์กำหนดที่อื่นหรือชื่ออื่น ใช้ตามนั้น (ความต้องการของพวกเขาชนะ) ถ้ามีเอกสารอยู่แล้ว แก้เฉพาะส่วนที่เกี่ยว ไม่เขียนใหม่ทั้งฉบับ

## กฎ

1. **ย้อนกลับไปหาต้นทางได้:** ทุกหน้าจอ endpoint ตาราง และโมดูลมีเหตุผลจากเวิร์กโฟลว์ ข้อมูล หรือข้อจำกัดที่ได้รับมา ไม่ออกแบบของที่ไม่มีใครขอ
2. **ง่ายที่สุดที่ตอบโจทย์:** เช่น monolith ก่อน microservices ทำตามลำดับความสำคัญที่ได้รับมา
3. **ของที่มีอยู่ชนะ:** ข้อจำกัดใน spec และโครงของโปรเจกต์เดิมมาก่อนความชอบของคุณ
4. **เรื่องเงินและบริการภายนอกเป็นของพวกเขา:** ถามก่อนเลือก พร้อมตัวเลือกที่แนะนำ
5. **ทุกส่วนต้องทดสอบได้:** ระบุ test framework ของแต่ละส่วนในหัวข้อ 1
6. **เวอร์ชันตรวจจริง:** ใช้เวอร์ชัน stable ล่าสุดที่ตรวจได้ตอนเขียน ไม่เดาจากความจำ

## ขั้นตอน

1. **อ่านอินพุต** ตาม "เริ่มจากสิ่งที่มี"
2. **ออกแบบหัวข้อ 1 → 6 ตามลำดับ** (หัวข้อหลังขึ้นกับหัวข้อก่อน) ส่วนที่ไม่เกี่ยวกับระบบนี้เขียน `- ไม่มี (<เหตุผล>)` ไม่ลบหัวข้อ
3. **ตรวจเอง** ก่อนเสนอ (เท่าที่อินพุตมีข้อมูลนั้น ข้อที่อินพุตไม่ได้พูดถึง ข้ามหรือจดเป็นสมมติฐาน ไม่ส่งกลับไปขั้นก่อน):
   - ทุกเวิร์กโฟลว์มีลำดับใน 4.1 หน้าจอใน 4.2 (ถ้ามี) endpoint ในข้อ 5 (ถ้ามี) และโมดูลในข้อ 3
   - ทุกข้อมูลมีที่เก็บในข้อ 6 และทุกตารางมีเวิร์กโฟลว์ใช้
   - ทุกสิทธิ์มีที่บังคับใช้ ทุกข้อคุณภาพมีการออกแบบรองรับ
   - เทคโนโลยีที่ข้อ 2–6 ใช้ อยู่ในข้อ 1 ครบ
4. **เสนอครั้งเดียว** ทั้งเอกสาร แยกให้เห็นว่าอะไรคือการตัดสินใจของคุณและอะไรเป็นสมมติฐาน
5. **ขอแก้** → แก้เฉพาะส่วนนั้น ตรวจข้อ 3 ใหม่ แล้วเสนอเฉพาะที่เปลี่ยน
6. **อนุมัติ** → เขียนไฟล์และ commit แล้วบอกหนึ่งบรรทัดว่าเสร็จ ขั้นถัดไปคือ superripple:writing-plans

## แก้ระหว่างทาง

ขอแก้ตอนไหนก็ได้ (ก่อนมีแผน ระหว่างทำ หรือหลังเสร็จ) ไม่ต้องย้อนไปขั้นก่อน:

- แก้เฉพาะหัวข้อที่กระทบและหัวข้อที่ขึ้นกับมัน
- ถ้ามีแผนหรืองานอยู่แล้ว บอกว่างานไหนได้รับผลกระทบ งานที่ไม่กระทบไม่ต้องทำซ้ำ
- เปลี่ยนเวอร์ชันหรือเทคโนโลยี → ตรวจเวอร์ชันใหม่ แล้วแก้แถวนั้นในหัวข้อ 1

## เนื้อหาเอกสาร 6 หัวข้อ

ใช้หัวข้อและเลขข้อตามนี้ ปรับจำนวนแถวและรายละเอียดตามระบบจริง

### 1. ภาษาและเทคโนโลยี
เลือกจากความเหมาะสมกับงาน เทคโนโลยีหลักของ human partner คือ **TypeScript**, **Rust** และ **MySQL** รองคือ **Go** และ **Python** เลือกตัวหลักก่อนเมื่อเหมาะ ใช้ตัวรองหรือตัวอื่นเมื่อเหมาะกว่าอย่างชัดเจน และบอกเหตุผลสั้นๆ (ของที่โปรเจกต์ใช้อยู่แล้วชนะ) framework และ library เลือกตามงาน

| ส่วนของระบบ | ภาษา / เทคโนโลยี | เวอร์ชัน | เหตุผลที่เหมาะกับงาน |
|---|---|---|---|

### 2. โครงสร้างโปรเจค
tree ของโฟลเดอร์ระดับบนและไฟล์สำคัญ แยกตามส่วนในข้อ 1 รวมโฟลเดอร์เทสต์

### 3. โค้ดเบส

| ส่วน / โมดูล | หน้าที่ |
|---|---|

หนึ่งโมดูลหนึ่งหน้าที่ interface เล็ก ทดสอบผ่าน interface ได้

> **skill เฉพาะทาง:** ออกแบบโค้ดเบสด้วย `superripple:codebase-design` (โมดูลลึก interface เล็ก ทดสอบผ่าน interface) แล้วสรุปผลลงตารางนี้

### 4. UX/UI

> **skill เฉพาะทาง:** งานที่มีหน้าจอ (เว็บ แอป dashboard component) ใช้ `superripple:impeccable` ออกแบบ UX/UI แล้วสรุปผลลงหัวข้อ 4.1 และ 4.2 ด้านล่าง ไม่มีหน้าจอ ข้ามไป

- **4.1 UX:** ลำดับการใช้งานจากมุมผู้ใช้ ไล่ตามเวิร์กโฟลว์ (หลายเวิร์กโฟลว์ แยกหัวข้อย่อย)
- **4.2 UI:** ตารางหน้าจอ (`หน้าจอ | รายละเอียด`) แสดงอะไร กดอะไรได้ ใครเห็น สถานะ loading / error / ว่าง

ไม่มีหน้าจอ (CLI / API ล้วน) → 4.1 เขียนลำดับคำสั่งที่ผู้ใช้พิมพ์ 4.2 `- ไม่มี (<เหตุผล>)`

### 5. API (ถ้ามี)

| Method | Endpoint | หน้าที่ |
|---|---|---|

บอกด้วยว่าใครเรียกได้

> **skill เฉพาะทาง:** งานที่มี API หรือบริการหลายส่วน ใช้ `superripple:backend-architect` ออกแบบ endpoint และขอบเขตบริการ แล้วสรุปผลลงตารางนี้

### 6. Database (ถ้ามี)

| ตาราง | คอลัมน์ | ความสัมพันธ์ |
|---|---|---|

คอลัมน์ระบุชนิดข้อมูลและ key (PK, FK, NOT NULL, UNIQUE) เงินเป็นจำนวนเต็มหน่วยย่อย

> **skill เฉพาะทาง:** งานที่มีฐานข้อมูลซับซ้อนหรือต้องเลือกชนิดฐานข้อมูล ใช้ `superripple:database-architect` แล้วสรุปผลลงตารางนี้ (MySQL เป็นตัวหลักก่อน)
