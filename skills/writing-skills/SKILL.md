# การเขียน Skill

## ภาพรวม

**การเขียน skill คือ Test-Driven Development ที่ใช้กับเอกสารกระบวนการ**

**skill ส่วนตัวอยู่ในไดเรกทอรี skills ของ runtime คุณ** (`~/.claude/skills/` บน Claude Code) — ดู [codex-tools.md](../using-superripple/references/codex-tools.md) หรือ [gemini-tools.md](../using-superripple/references/gemini-tools.md) สำหรับพาธบน runtime เหล่านั้น Codex, Copilot CLI และ Gemini CLI ต่างก็รู้จัก `~/.agents/skills/` เป็นชื่อแทนข้าม runtime ด้วย

คุณเขียนเทสต์เคส (สถานการณ์กดดันด้วย subagent) ดูมันล้มเหลว (พฤติกรรมตั้งต้น) เขียน skill (เอกสาร) ดูเทสต์ผ่าน (agent ทำตาม) และ refactor (ปิดช่องโหว่)

**หลักการ:** ถ้าไม่ได้ดู agent ล้มเหลวเมื่อไม่มี skill คุณไม่รู้ว่า skill สอนสิ่งที่ถูกหรือเปล่า

**ความรู้พื้นฐานที่ต้องมี:** คุณต้องเข้าใจ superripple:test-driven-development ก่อนใช้ skill นี้ skill นั้นกำหนดวงจร RED-GREEN-REFACTOR พื้นฐาน skill นี้ปรับ TDD ให้ใช้กับเอกสาร

**แนวทางทางการ:** สำหรับแนวปฏิบัติที่ดีที่สุดในการเขียน skill ของ Anthropic ดู references/anthropic-best-practices.md เอกสารนี้ให้รูปแบบและแนวทางเพิ่มเติมที่เสริมแนวทางที่ใช้ TDD เป็นหลักของ skill นี้

## Skill คืออะไร?

**skill** คือคู่มืออ้างอิงสำหรับเทคนิค รูปแบบ หรือเครื่องมือที่พิสูจน์แล้ว skill ช่วยให้ agent ในอนาคตหาและใช้แนวทางที่ได้ผล

**skill คือ:** เทคนิคที่ใช้ซ้ำได้ รูปแบบ เครื่องมือ คู่มืออ้างอิง

**skill ไม่ใช่:** เรื่องเล่าว่าคุณเคยแก้ปัญหาหนึ่งอย่างไร

## การจับคู่ TDD กับ Skill

| แนวคิด TDD | การสร้าง Skill |
|-------------|----------------|
| **เทสต์เคส** | สถานการณ์กดดันด้วย subagent |
| **โค้ด production** | เอกสาร skill (SKILL.md) |
| **เทสต์ล้มเหลว (RED)** | agent ฝ่าฝืนกฎเมื่อไม่มี skill (พื้นฐาน) |
| **เทสต์ผ่าน (GREEN)** | agent ทำตามเมื่อมี skill |
| **Refactor** | ปิดช่องโหว่ขณะรักษาการทำตาม |
| **เขียนเทสต์ก่อน** | รันสถานการณ์พื้นฐาน "ก่อน" เขียน skill |
| **ดูมันล้มเหลว** | บันทึกข้ออ้างที่ agent ใช้อย่างแน่นอน |
| **โค้ดน้อยที่สุด** | เขียน skill ที่ตอบการฝ่าฝืนเฉพาะเหล่านั้น |
| **ดูมันผ่าน** | ตรวจว่า agent ทำตามแล้ว |
| **วงจร refactor** | พบข้ออ้างใหม่ → อุด → ตรวจซ้ำ |

กระบวนการสร้าง skill ทั้งหมดทำตาม RED-GREEN-REFACTOR

## เมื่อไหร่ควรสร้าง Skill

**สร้างเมื่อ:**
- เทคนิคไม่ชัดเจนโดยสัญชาตญาณสำหรับคุณ
- คุณจะอ้างถึงอีกข้ามโปรเจกต์
- รูปแบบใช้ได้กว้าง (ไม่เฉพาะโปรเจกต์)
- คนอื่นจะได้ประโยชน์

**ไม่ต้องสร้างสำหรับ:**
- วิธีแก้ครั้งเดียว
- แนวปฏิบัติมาตรฐานที่มีเอกสารที่อื่นดีอยู่แล้ว
- ธรรมเนียมเฉพาะโปรเจกต์ (ใส่ในไฟล์คำสั่งของคุณ)
- ข้อจำกัดแบบกลไก (ถ้าบังคับได้ด้วย regex/validation ให้ทำอัตโนมัติ — เก็บเอกสารไว้สำหรับการใช้ดุลยพินิจ)

## ชนิดของ Skill

### เทคนิค (Technique)
วิธีการที่เป็นรูปธรรมพร้อมขั้นตอน (condition-based-waiting, root-cause-tracing)

### รูปแบบ (Pattern)
วิธีคิดเกี่ยวกับปัญหา (flatten-with-flags, test-invariants)

### อ้างอิง (Reference)
เอกสาร API คู่มือไวยากรณ์ เอกสารเครื่องมือ (office docs)

## โครงสร้างไดเรกทอรี


```
skills/
  skill-name/
    SKILL.md              # อ้างอิงหลัก (จำเป็น)
    supporting-file.*     # เฉพาะเมื่อจำเป็น
```

**namespace แบบแบน** - ทุก skill อยู่ใน namespace เดียวที่ค้นหาได้

**แยกไฟล์สำหรับ:**
1. **อ้างอิงหนัก** (100+ บรรทัด) - เอกสาร API ไวยากรณ์ครบถ้วน
2. **เครื่องมือใช้ซ้ำ** - สคริปต์ ยูทิลิตี เทมเพลต

**เก็บไว้ในตัว:**
- หลักการและแนวคิด
- รูปแบบโค้ด (< 50 บรรทัด)
- อย่างอื่นทั้งหมด

## การเขียน SKILL.md

`description` ของ skill บอกเฉพาะว่าเมื่อไหร่ควรใช้: เงื่อนไขกระตุ้นและอาการ ขึ้นต้นด้วย "Use when..." มันไม่เคยสรุปเวิร์กโฟลว์ของ skill เพราะ agent ที่อ่านสรุปเวิร์กโฟลว์จะทำตามสรุปแทนที่จะอ่าน skill

เมื่อคุณเขียนหรือเปลี่ยน frontmatter ชื่อ หรือ description ของ skill หรือต้องลดขนาด ให้อ่าน [references/discovery.md](references/discovery.md): เทมเพลต SKILL.md แนวทาง description และคีย์เวิร์ด การตั้งชื่อ งบ token และการอ้างอิงข้าม skill

## แผนผังลำดับ (Flowchart)

เมื่อเพิ่มหรือเปลี่ยน flowchart ใน skill ให้อ่าน [references/flowcharts.md](references/flowcharts.md) ก่อน: เมื่อไหร่ flowchart คุ้มค่า ธรรมเนียมของ graphviz และวิธีเรนเดอร์

## ตัวอย่างโค้ด

**ตัวอย่างยอดเยี่ยมหนึ่งอันดีกว่าตัวอย่างธรรมดาหลายอัน**

เลือกภาษาที่เกี่ยวข้องที่สุด:
- เทคนิคการทดสอบ → TypeScript/JavaScript
- การดีบักระบบ → Shell/Python
- การประมวลผลข้อมูล → Python

**ตัวอย่างที่ดี:**
- สมบูรณ์และรันได้
- คอมเมนต์ดีอธิบายว่า "ทำไม"
- มาจากสถานการณ์จริง
- แสดงรูปแบบชัดเจน
- พร้อมดัดแปลง (ไม่ใช่เทมเพลตทั่วไป)

**อย่า:**
- ทำในภาษา 5+ ภาษา
- สร้างเทมเพลตแบบเติมคำในช่องว่าง
- เขียนตัวอย่างที่แต่งขึ้น

คุณเก่งเรื่องการแปลงภาษา - ตัวอย่างยอดเยี่ยมหนึ่งอันก็พอ

## การจัดไฟล์

### Skill ที่ครบในตัว
```
defense-in-depth/
  SKILL.md    # ทุกอย่างอยู่ในตัว
```
เมื่อ: เนื้อหาทั้งหมดใส่ได้ ไม่ต้องมีอ้างอิงหนัก

### Skill ที่มีเครื่องมือใช้ซ้ำ
```
condition-based-waiting/
  SKILL.md    # ภาพรวม + รูปแบบ
  example.ts  # ตัวช่วยที่ใช้งานได้ให้ดัดแปลง
```
เมื่อ: เครื่องมือเป็นโค้ดที่ใช้ซ้ำได้ ไม่ใช่แค่เรื่องเล่า

### Skill ที่มีอ้างอิงหนัก
```
pptx/
  SKILL.md       # ภาพรวม + เวิร์กโฟลว์
  pptxgenjs.md   # อ้างอิง API 600 บรรทัด
  ooxml.md       # โครงสร้าง XML 500 บรรทัด
  scripts/       # เครื่องมือรันได้
```
เมื่อ: เนื้อหาอ้างอิงใหญ่เกินใส่ในตัว

เรียกสคริปต์ที่แถมมาผ่านตัวแปลภาษาของมันในเนื้อความ (`bash scripts/tool.sh`, `node scripts/tool.js`) ห้ามเรียกด้วยพาธเปล่าๆ: ตัวแพ็กเกจปลั๊กอินของ harness บางตัวลบ executable bit และ `scripts/tool.sh` แบบเปล่าล้มเหลวที่นั่นด้วย `Permission denied`

## กฎเหล็ก (เหมือน TDD)

```
ห้ามมี SKILL ถ้ายังไม่มีเทสต์ที่ล้มเหลวก่อน
```

ใช้กับ skill ใหม่ "และ" การแก้ skill ที่มีอยู่

เขียน skill ก่อนทดสอบ? ลบมัน เริ่มใหม่
แก้ skill โดยไม่ทดสอบ? ละเมิดเหมือนกัน

**ไม่มีข้อยกเว้น:**
- ไม่ใช่สำหรับ "เพิ่มเล็กน้อย"
- ไม่ใช่สำหรับ "แค่เพิ่มหัวข้อ"
- ไม่ใช่สำหรับ "อัปเดตเอกสาร"
- อย่าเก็บการเปลี่ยนที่ไม่ได้ทดสอบเป็น "ตัวอ้างอิง"
- อย่า "ดัดแปลง" ขณะรันเทสต์
- ลบคือลบ

**ความรู้พื้นฐานที่ต้องมี:** skill superripple:test-driven-development อธิบายว่าทำไมสำคัญ หลักการเดียวกันใช้กับเอกสาร

## การทดสอบ Skill ทุกชนิด

skill ต่างชนิดต้องการวิธีทดสอบต่างกัน:

### Skill ที่บังคับวินัย (กฎ/ข้อกำหนด)

**ตัวอย่าง:** TDD, verification-before-completion, designing-before-coding

**ทดสอบด้วย:**
- คำถามเชิงวิชาการ: เข้าใจกฎไหม?
- สถานการณ์กดดัน: ทำตามเมื่ออยู่ภายใต้ความเครียดไหม?
- แรงกดดันหลายอย่างรวมกัน: เวลา + sunk cost + ความเหนื่อย
- ระบุข้ออ้างและเพิ่มข้อโต้แย้งที่ชัดเจน

**เกณฑ์สำเร็จ:** agent ทำตามกฎภายใต้แรงกดดันสูงสุด

### Skill เทคนิค (คู่มือวิธีทำ)

**ตัวอย่าง:** condition-based-waiting, root-cause-tracing, defensive-programming

**ทดสอบด้วย:**
- สถานการณ์การประยุกต์: ใช้เทคนิคได้ถูกต้องไหม?
- สถานการณ์แปรผัน: จัดการ edge case ได้ไหม?
- ทดสอบข้อมูลที่ขาด: คำแนะนำมีช่องว่างไหม?

**เกณฑ์สำเร็จ:** agent ประยุกต์เทคนิคกับสถานการณ์ใหม่ได้สำเร็จ

### Skill รูปแบบ (แบบจำลองความคิด)

**ตัวอย่าง:** reducing-complexity, แนวคิด information-hiding

**ทดสอบด้วย:**
- สถานการณ์การจดจำ: รู้ไหมว่าเมื่อไหร่รูปแบบใช้ได้?
- สถานการณ์การประยุกต์: ใช้แบบจำลองความคิดได้ไหม?
- ตัวอย่างตรงข้าม: รู้ไหมว่าเมื่อไหร่ "ไม่ควร" ใช้?

**เกณฑ์สำเร็จ:** agent ระบุได้ถูกต้องว่าเมื่อไหร่/อย่างไรจะใช้รูปแบบ

### Skill อ้างอิง (เอกสาร/API)

**ตัวอย่าง:** เอกสาร API คู่มือคำสั่ง คู่มือไลบรารี

**ทดสอบด้วย:**
- สถานการณ์การค้นหา: หาข้อมูลที่ถูกได้ไหม?
- สถานการณ์การประยุกต์: ใช้สิ่งที่พบได้ถูกต้องไหม?
- ทดสอบช่องว่าง: กรณีใช้งานทั่วไปครอบคลุมไหม?

**เกณฑ์สำเร็จ:** agent หาและประยุกต์ข้อมูลอ้างอิงได้ถูกต้อง

## ข้ออ้างที่พบบ่อยสำหรับการข้ามการทดสอบ

| ข้ออ้าง | ความจริง |
|--------|---------|
| "skill ชัดเจนอยู่แล้ว" | ชัดสำหรับคุณ ≠ ชัดสำหรับ agent อื่น ทดสอบ |
| "มันแค่อ้างอิง" | อ้างอิงมีช่องว่างและส่วนที่ไม่ชัดได้ ทดสอบการค้นหา |
| "การทดสอบเกินความจำเป็น" | skill ที่ไม่ได้ทดสอบมีปัญหา เสมอ ทดสอบ 15 นาทีประหยัดหลายชั่วโมง |
| "จะทดสอบถ้ามีปัญหา" | ปัญหา = agent ใช้ skill ไม่ได้ ทดสอบ "ก่อน" ใช้งาน |
| "น่าเบื่อเกินจะทดสอบ" | การทดสอบน่าเบื่อน้อยกว่าการดีบัก skill แย่บน production |
| "มั่นใจว่าดี" | ความมั่นใจเกินเหตุรับประกันปัญหา ทดสอบอยู่ดี |
| "รีวิวเชิงวิชาการพอ" | การอ่าน ≠ การใช้ ทดสอบสถานการณ์การประยุกต์ |
| "ไม่มีเวลาทดสอบ" | การใช้ skill ที่ไม่ได้ทดสอบเสียเวลาแก้ทีหลังมากกว่า |

**ทั้งหมดนี้หมายความว่า: ทดสอบก่อนใช้งาน ไม่มีข้อยกเว้น**

## ให้รูปแบบตรงกับความล้มเหลว

ก่อนเขียนคำแนะนำ ให้จำแนกความล้มเหลวพื้นฐาน รูปแบบที่ทำให้ความล้มเหลวหนึ่งชนิดกันกระสุนได้ อาจย้อนกลับร้ายต่อความล้มเหลวอีกชนิดอย่างวัดได้

| ความล้มเหลวพื้นฐาน | รูปแบบที่ถูก | รูปแบบที่ผิด |
|---|---|---|
| ข้าม/ฝ่าฝืนกฎภายใต้แรงกดดัน (รู้ดีกว่า แต่ทำอยู่ดี) | ข้อห้าม + ตารางข้ออ้าง + สัญญาณเตือน (ดู references/bulletproofing.md) | คำแนะนำอ่อน ("ควร...", "พิจารณา...") |
| ทำตาม แต่ผลลัพธ์มีรูปร่างผิด (พรอมต์บวม คำตัดสินจมอยู่ ทวน spec ซ้ำ) | สูตรเชิงบวกหรือสัญญา: บอกว่าผลลัพธ์ "คือ" อะไร — ส่วนต่างๆ ตามลำดับ | รายการข้อห้าม ("อย่าทวนซ้ำ", "อย่าเล่า") |
| ละองค์ประกอบที่จำเป็นของสิ่งที่พวกเขาผลิตอยู่แล้ว | เชิงโครงสร้าง: ฟิลด์หรือช่อง REQUIRED ในเทมเพลตที่พวกเขากรอก | ข้อความเตือนในร้อยแก้วใกล้เทมเพลต |
| พฤติกรรมควรขึ้นกับเงื่อนไข | เงื่อนไขที่ผูกกับสิ่งที่สังเกตได้ ("ถ้ามี brief ให้อ้างถึงมัน") | กฎไม่มีเงื่อนไข + ข้อความยกเว้น |

**ทำไมข้อห้ามย้อนกลับร้ายกับปัญหาการจัดรูปทรง:** ภายใต้แรงจูงใจที่แข่งกัน ("ทำให้พรอมต์ครบในตัว") agent ต่อรองกับ "อย่าทำ X" ในการทดสอบถ้อยคำแบบเทียบหัวต่อหัวกับคำแนะนำการส่งพรอมต์ กลุ่มข้อห้ามผลิตเนื้อหาที่ไม่ต้องการมากกว่ากลุ่มสูตรอย่างชัดเจน (การกระจายแยกจากกันสมบูรณ์) และมีแนวโน้มแย่กว่าแม้กลุ่มควบคุมที่ไม่มีคำแนะนำ — ทดสอบกรณีของคุณเองแทนการสมมติ แต่อย่าหยิบข้อห้ามเป็นค่าตั้งต้น สูตรไม่เหลืออะไรให้ต่อรอง: ผลลัพธ์ตรงกับรูปทรงที่ระบุหรือไม่ตรง

**กฎสำหรับรูปแบบใดก็ตามที่เลือก:**
- **ไม่มีข้อความแบบมีเงื่อนไขอ่อน** "อย่าทำ X เว้นแต่สำคัญ" เปิดการต่อรองอีกครั้ง — การเติมข้อความแบบมีเงื่อนไขเดียวลงในสูตรที่ชนะทำให้มันแย่จากสม่ำเสมอเป็นผันผวนในการทดสอบถ้อยคำเดียวกัน แสดงข้อยกเว้นจริงเป็นเงื่อนไขของมันเองที่ผูกกับสิ่งที่สังเกตได้
- **ข้อความยกเว้นไม่จำกัดขอบเขต** "ขีดจำกัดนี้ไม่ใช้กับบล็อกโค้ด" ก็ยังกดบล็อกโค้ดอยู่ดี ถ้าส่วนหนึ่งของผลลัพธ์ต้องได้รับการยกเว้น ให้จัดโครงสร้างใหม่เพื่อให้กฎเข้าไม่ถึงมัน

## การทำให้กันกระสุนต่อการหาเหตุผลเข้าข้างตัวเอง

เมื่อความล้มเหลวพื้นฐานเป็นความล้มเหลวด้านวินัย ให้อ่าน [references/bulletproofing.md](references/bulletproofing.md) ก่อนเขียนคำแนะนำ: การปิดช่องโหว่ เส้นแบ่งเจตนารมณ์กับตัวอักษร ตารางข้ออ้าง และรายการสัญญาณเตือน

## RED-GREEN-REFACTOR สำหรับ Skill

ทำตามวงจร TDD:

### RED: เขียนเทสต์ที่ล้มเหลว (พื้นฐาน)

รันสถานการณ์กดดันด้วย subagent "โดยไม่มี" skill บันทึกพฤติกรรมที่แน่นอน:
- พวกเขาเลือกอะไร?
- พวกเขาใช้ข้ออ้างอะไร (ตรงตัว)?
- แรงกดดันแบบไหนกระตุ้นการฝ่าฝืน?

นี่คือ "ดูเทสต์ล้มเหลว" - คุณต้องเห็นสิ่งที่ agent ทำโดยธรรมชาติก่อนเขียน skill

### GREEN: เขียน Skill น้อยที่สุด

เขียน skill ที่ตอบข้ออ้างเฉพาะเหล่านั้น อย่าเพิ่มเนื้อหาสำหรับกรณีสมมติ

รันสถานการณ์เดิม "โดยมี" skill agent ควรทำตามแล้ว

### REFACTOR: ปิดช่องโหว่

agent พบข้ออ้างใหม่? เพิ่มข้อโต้แย้งที่ชัดเจน ทดสอบซ้ำจนกันกระสุน

### ทดสอบถ้อยคำแบบ Micro ก่อนสถานการณ์เต็ม

การรันสถานการณ์กดดันเต็มคือด่านสุดท้าย แต่ช้าและแพงต่อรอบ ตรวจถ้อยคำเองก่อนด้วยการทดสอบ micro:

1. **หนึ่งตัวอย่าง context หน้าใหม่ต่อการเรียก** — เรียก API ดิบ หรือ subagent ครั้งเดียวถ้าไม่มีสิทธิ์ API system prompt = บริบทจริงที่คำแนะนำจะอยู่ (skill หรือเทมเพลตพรอมต์เต็ม ไม่ใช่คำแนะนำโดดๆ) ข้อความผู้ใช้ = งานที่ล่อให้เกิดความล้มเหลว
2. **ต้องมีกลุ่มควบคุมที่ไม่มีคำแนะนำเสมอ** ถ้ากลุ่มควบคุมไม่แสดงความล้มเหลว ก็ไม่มีอะไรต้องแก้ — หยุด อย่าเขียนคำแนะนำ
3. **5+ รอบต่อแบบ** ตัวอย่างเดียวโกหก
4. **อ่านทุกรายการที่ติดธงด้วยมือ** ให้คะแนนด้วยโปรแกรมได้ แต่ echo ของเทมเพลตและตัวอย่างตรงข้ามที่อ้างอิงปลอมตัวเป็นผลตรง การนับอัตโนมัติอย่างเดียวประเมินทั้งความล้มเหลวและความสำเร็จเกินจริง
5. **ความแปรปรวนคือเมตริก** เมื่อคำแนะนำได้ผล ทุกรอบลู่เข้าสู่รูปทรงเดียวกัน ห้าการตีความต่างกันในห้ารอบหมายความว่าถ้อยคำไม่ผูกมัด — ขันรูปแบบให้แน่นก่อนเพิ่มคำ

การทดสอบ micro ตรวจถ้อยคำ มันไม่แทนสถานการณ์กดดันสำหรับ skill ด้านวินัย

**วิธีการทดสอบ:** ดู [references/testing-skills-with-subagents.md](references/testing-skills-with-subagents.md) สำหรับวิธีการทดสอบฉบับสมบูรณ์:
- วิธีเขียนสถานการณ์กดดัน
- ชนิดแรงกดดัน (เวลา sunk cost อำนาจ ความเหนื่อย)
- การอุดช่องโหว่อย่างเป็นระบบ
- เทคนิคการทดสอบเมตา

## รูปแบบที่ไม่ดี (Anti-Patterns)

### ❌ ตัวอย่างแบบเรื่องเล่า
"ใน session 2025-10-03 เราพบว่า projectDir ที่ว่างทำให้..."
**ทำไมไม่ดี:** เฉพาะเจาะจงเกินไป ใช้ซ้ำไม่ได้

### ❌ การเจือจางด้วยหลายภาษา
example-js.js, example-py.py, example-go.go
**ทำไมไม่ดี:** คุณภาพธรรมดา เป็นภาระการดูแล

### ❌ โค้ดใน Flowchart
```dot
step1 [label="import fs"];
step2 [label="read file"];
```
**ทำไมไม่ดี:** คัดลอกวางไม่ได้ อ่านยาก

### ❌ ป้ายชื่อทั่วไป
helper1, helper2, step3, pattern4
**ทำไมไม่ดี:** ป้ายชื่อควรมีความหมายเชิงความหมาย

## หยุด: ก่อนไป Skill ถัดไป

**หลังเขียน skill ใดๆ คุณ "ต้อง" หยุดและทำกระบวนการนำไปใช้ให้เสร็จ**

**ห้าม:**
- สร้างหลาย skill เป็นชุดโดยไม่ทดสอบแต่ละอัน
- ไป skill ถัดไปก่อนที่อันปัจจุบันจะถูกตรวจสอบ
- ข้ามการทดสอบเพราะ "การทำเป็นชุดมีประสิทธิภาพกว่า"

**เช็กลิสต์การนำไปใช้ด้านล่างบังคับสำหรับ skill "แต่ละ" อัน**

การใช้ skill ที่ไม่ได้ทดสอบ = การใช้โค้ดที่ไม่ได้ทดสอบ มันละเมิดมาตรฐานคุณภาพ

## เช็กลิสต์การสร้าง Skill (ปรับจาก TDD)

**สำคัญ: สร้าง todo สำหรับทุกรายการในเช็กลิสต์ด้านล่าง**

**เฟส RED - เขียนเทสต์ที่ล้มเหลว:**
- [ ] สร้างสถานการณ์กดดัน (3+ แรงกดดันรวมกันสำหรับ skill ด้านวินัย)
- [ ] รันสถานการณ์ "โดยไม่มี" skill - บันทึกพฤติกรรมพื้นฐานตรงตัว
- [ ] ระบุรูปแบบในข้ออ้าง/ความล้มเหลว

**เฟส GREEN - เขียน Skill น้อยที่สุด:**
- [ ] ชื่อใช้เฉพาะตัวอักษร ตัวเลข และขีดกลาง (ไม่มีวงเล็บ/อักขระพิเศษ)
- [ ] YAML frontmatter มีฟิลด์ `name` และ `description` ที่จำเป็น (สูงสุด 1024 ตัวอักษร; ดู [spec](https://agentskills.io/specification))
- [ ] Description ขึ้นต้นด้วย "Use when..." และมีตัวกระตุ้น/อาการเฉพาะ
- [ ] Description เขียนในบุรุษที่สาม
- [ ] คีย์เวิร์ดตลอดเพื่อการค้นหา (error อาการ เครื่องมือ)
- [ ] ภาพรวมชัดเจนพร้อมหลักการ
- [ ] ตอบความล้มเหลวพื้นฐานเฉพาะที่ระบุใน RED
- [ ] รูปแบบคำแนะนำตรงกับชนิดความล้มเหลว (ดู "ให้รูปแบบตรงกับความล้มเหลว")
- [ ] สำหรับคำแนะนำที่กำหนดพฤติกรรม: ทดสอบถ้อยคำ micro กับกลุ่มควบคุมที่ไม่มีคำแนะนำ (5+ รอบ อ่านทุกรายการที่ติดธงด้วยมือ) — ไม่เกี่ยวสำหรับ skill อ้างอิงล้วน
- [ ] โค้ดในตัว หรือลิงก์ไปไฟล์แยก
- [ ] ตัวอย่างยอดเยี่ยมหนึ่งอัน (ไม่ใช่หลายภาษา)
- [ ] รันสถานการณ์ "โดยมี" skill - ตรวจว่า agent ทำตามแล้ว

**เฟส REFACTOR - ปิดช่องโหว่:**
- [ ] ระบุข้ออ้าง "ใหม่" จากการทดสอบ
- [ ] เพิ่มข้อโต้แย้งที่ชัดเจน (ถ้าเป็น skill ด้านวินัย)
- [ ] สร้างตารางข้ออ้างจากทุกรอบการทดสอบ
- [ ] สร้างรายการสัญญาณเตือน
- [ ] ทดสอบซ้ำจนกันกระสุน

**การตรวจคุณภาพ:**
- [ ] Flowchart เล็กเฉพาะเมื่อการตัดสินใจไม่ชัดเจน
- [ ] ตารางอ้างอิงด่วน
- [ ] ส่วนความผิดพลาดที่พบบ่อย
- [ ] ไม่มีการเล่าเรื่อง
- [ ] ไฟล์สนับสนุนเฉพาะเครื่องมือหรืออ้างอิงหนัก

**การนำไปใช้:**
- [ ] Commit skill ลง git และ push ไป fork ของคุณ (ถ้าตั้งค่าไว้)
- [ ] พิจารณาส่งกลับผ่าน PR (ถ้าเป็นประโยชน์กว้าง)

## กระบวนการค้นพบ

agent ในอนาคตหา skill ของคุณอย่างไร:

1. **เจอปัญหา** ("เทสต์ไม่นิ่ง")
2. **ค้นหา skill** (grep description เรียกดูหมวดหมู่)
3. **พบ SKILL** (description ตรงกัน)
4. **สแกนภาพรวม** (เกี่ยวข้องไหม?)
5. **อ่านรูปแบบ** (ตารางอ้างอิงด่วน)
6. **โหลดตัวอย่าง** (เฉพาะเมื่อลงมือ)

**ปรับให้เหมาะกับกระบวนการนี้** - ใส่คำที่ค้นหาได้ไว้ต้นๆ และบ่อยๆ
