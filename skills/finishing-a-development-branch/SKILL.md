# การจบ Branch พัฒนา

## ภาพรวม

**หลักการ:** ตรวจเทสต์ → ตรวจสภาพแวดล้อม → เสนอตัวเลือก → ทำตามที่เลือก → ล้างของ

**ประกาศตอนเริ่ม:** "ผมใช้ skill finishing-a-development-branch เพื่อจบงานนี้"

## ขั้น 1: ตรวจเทสต์

รันชุดเทสต์ทั้งหมดของโปรเจกต์ (`npm test` / `cargo test` / `pytest` / `go test ./...`)

**ถ้าเทสต์ล้มเหลว** ให้รายงานความล้มเหลวแล้วหยุด - เมนูมาหลังชุดเทสต์เขียวเท่านั้น:

```
เทสต์ล้มเหลว (<N> รายการ) ต้องแก้ก่อนจบงาน:

[แสดงรายการที่ล้มเหลว]
```

**ถ้าเทสต์ผ่าน:** ไปขั้น 2

## ขั้น 2: ตรวจสภาพแวดล้อม

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
# เก็บค่าไว้ตอนนี้ ขณะยังอยู่ใน workspace — ขั้น 5 เปลี่ยนไดเรกทอรี
# ก่อนที่การล้าง (ขั้น 6) จะต้องใช้ค่านี้
WORKTREE_PATH=$(git rev-parse --show-toplevel)
```

ค่านี้กำหนดว่าจะแสดงเมนูไหนและล้างอย่างไร:

| สถานะ | เมนู | การล้าง |
|-------|------|---------|
| `GIT_DIR == GIT_COMMON` (repo ปกติ) | 3 ตัวเลือกมาตรฐาน | ไม่มี worktree ให้ล้าง |
| `GIT_DIR != GIT_COMMON`, branch มีชื่อ | 3 ตัวเลือกมาตรฐาน | ตามที่มา (ดูขั้น 6) |
| `GIT_DIR != GIT_COMMON`, detached HEAD | ลดเหลือ 2 ตัวเลือก (ไม่มี merge) | จัดการจากภายนอก — ปล่อยไว้ |

## ขั้น 3: หา Base Branch

base branch คือ branch ที่งานนี้แตกออกมา — มักระบุไว้ในแผน บทสนทนา หรือ upstream ของ branch ถ้ายังไม่รู้ ให้ถาม: "branch นี้แตกจาก <เดาที่ดีที่สุดของคุณ> ถูกไหม?" ยืนยันก่อน merge: การ merge เข้า base ผิดแก้คืนยาก

## ขั้น 4: เสนอตัวเลือก

**repo ปกติและ worktree ที่มี branch ชื่อ — เสนอ 3 ตัวเลือกนี้เท่านั้น:**

```
พัฒนาเสร็จแล้ว ต้องการทำอะไร?

1. Merge กลับเข้า <base-branch> ในเครื่อง
2. Push และสร้าง Pull Request
3. เก็บ branch ไว้อย่างนี้ (ผมจะจัดการเองทีหลัง)

เลือกข้อไหน?
```

**Detached HEAD — เสนอ 2 ตัวเลือกนี้เท่านั้น:**

```
พัฒนาเสร็จแล้ว คุณอยู่บน detached HEAD (workspace ที่จัดการจากภายนอก)

1. Push เป็น branch ใหม่และสร้าง Pull Request
2. เก็บไว้อย่างนี้ (ผมจะจัดการเองทีหลัง)

เลือกข้อไหน?
```

เสนอเมนูตามที่เขียนไว้ทุกตัวอักษร — กระชับ และทุกตัวเลือกมาจากรายการข้างบน การทิ้งงานเกิดขึ้นเมื่อ human partner ขออย่างชัดเจนเท่านั้น (ดู "ถ้า human partner ขอให้ทิ้งงาน" ด้านล่าง) รอคำตอบของพวกเขา การตัดสินใจเรื่องการรวมงานเป็นของพวกเขา

## ขั้น 5: ทำตามที่เลือก

### ตัวเลือก 1: Merge ในเครื่อง

```bash
# หา root ของ repo หลักเพื่อความปลอดภัยของ CWD
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"

# Merge ก่อน — ยืนยันว่าสำเร็จก่อนลบอะไร
git checkout <base-branch>
git pull
git merge <feature-branch>

# ตรวจเทสต์บนผลลัพธ์ที่ merge แล้ว
<test command>
```

ถ้าเทสต์ล้มเหลวบนผลลัพธ์ที่ merge: หยุด ปล่อย worktree และ branch ไว้ แล้วสืบสวน — ยังไม่มีอะไรถูก push ดังนั้น merge นี้อยู่ในเครื่องและกู้คืนได้

เมื่อผลลัพธ์ที่ merge เขียวแล้ว: ล้าง worktree (ขั้น 6) แล้วลบ branch:

```bash
git branch -d <feature-branch>
```

### ตัวเลือก 2: Push และสร้าง PR

```bash
git push -u origin <feature-branch>
# จาก detached HEAD ให้ตั้งชื่อ branch ใหม่บน remote:
# git push origin HEAD:refs/heads/<new-branch>
```

จากนั้นสร้าง pull/merge request ไปยัง <base-branch> ด้วยเครื่องมือของ forge นั้น — CLI ถ้ามี หรือ URL สำหรับสร้างที่ forge ส่วนใหญ่พิมพ์ตอน push — ตามเทมเพลต PR และธรรมเนียมของ repo ถ้ามี แล้วรายงาน URL ให้ human partner

เก็บ worktree ไว้ — human partner จะแก้ตามข้อเสนอแนะของ PR ที่นั่น

### ตัวเลือก 3: เก็บไว้อย่างนี้

รายงาน: "เก็บ branch <name> ไว้ Worktree ยังอยู่ที่ <path>"

### ถ้า human partner ขอให้ทิ้งงาน

เส้นทางนี้มีไว้ตอบคำขอที่ชัดเจนให้ทิ้งงานเท่านั้น ยืนยันก่อน:

```
การกระทำนี้จะลบถาวร:
- Branch <name>
- Commit ทั้งหมด: <commit-list>
- Worktree ที่ <path>

พิมพ์ 'discard' เพื่อยืนยัน
```

รอการยืนยันตามคำนั้นเป๊ะๆ เมื่อได้รับ:

```bash
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"
```

จากนั้นล้าง worktree (ขั้น 6) และลบ branch แบบบังคับ:

```bash
git branch -D <feature-branch>
```

## ขั้น 6: ล้าง Workspace

**ทำสำหรับตัวเลือก 1 และการทิ้งที่ยืนยันแล้ว** ตัวเลือก 2 และ 3 เก็บ worktree ไว้เสมอ ทั้งสองกรณีเปลี่ยนไดเรกทอรีไปที่ root ของ repo หลักแล้ว — การลบ worktree ต้องรันจากนอก worktree — และใช้ค่า `GIT_DIR`/`GIT_COMMON`/`WORKTREE_PATH` ที่เก็บไว้ในขั้น 2 ก่อนการเปลี่ยนไดเรกทอรี

**ถ้า `GIT_DIR == GIT_COMMON`:** repo ปกติ ไม่มี worktree ให้ล้าง เสร็จ

**ถ้า `WORKTREE_PATH` อยู่ใต้ `.worktrees/` หรือ `worktrees/`:** superripple สร้าง worktree นี้ — เราดูแลการล้าง:

```bash
git worktree remove "$WORKTREE_PATH"
git worktree prune  # ซ่อมแซมตัวเอง: ล้างการลงทะเบียนที่ค้าง
```

**ถ้าการลบถูกปฏิเสธ** (`contains modified or untracked files`): worktree มีไฟล์ที่ไม่มีที่อื่น — แผน บันทึก หรืองานร่างที่ยังไม่ commit ห้ามใช้ `--force` โดยพลการ แสดงให้ human partner เห็นว่าอะไรเสี่ยงและถาม:

```bash
git -C "$WORKTREE_PATH" status --porcelain -uall
```

```
การลบ worktree ถูกปฏิเสธ — ไฟล์เหล่านี้ไม่เคย commit:

<รายการไฟล์>

1. Commit ลง <branch> ก่อนล้าง
2. ย้ายไปไว้ใน <root ของ repo หลัก>
3. ลบทิ้ง (กู้คืนไม่ได้)

เลือกข้อไหน?
```

ทำตามที่เลือก แล้วค่อยลบ worktree

**กรณีอื่น:** สภาพแวดล้อมโฮสต์เป็นเจ้าของ workspace นี้ — ปล่อยไว้ ถ้าแพลตฟอร์มมีเครื่องมือออกจาก workspace ให้ใช้

## ตารางอ้างอิงด่วน

| ตัวเลือก | Merge | Push | เก็บ Worktree | ล้าง Branch |
|--------|-------|------|---------------|----------------|
| 1. Merge ในเครื่อง | ใช่ | - | - | ใช่ |
| 2. สร้าง PR | - | ใช่ | ใช่ | - |
| 3. เก็บไว้อย่างนี้ | - | - | ใช่ | - |
| ทิ้ง (เมื่อขออย่างชัดเจนเท่านั้น) | - | - | - | ใช่ (บังคับ) |

## ข้ออ้างที่พบบ่อย

| ข้ออ้าง | ความจริง |
|--------|---------|
| "เทสต์ผ่านเมื่อก่อนหน้านี้ใน session" | รันชุดเทสต์บนต้นไม้ที่กำลังจะรวม การรันที่เขียวพิสูจน์ได้เฉพาะต้นไม้ที่มันรัน |
| "เห็นชัดว่าพวกเขาอยากให้ merge" | การรวมงานเป็นการตัดสินใจของ human partner เสนอเมนูแล้วรอ |
| "ดูเหมือนพวกเขาเลิกสนใจฟีเจอร์นี้ — จะเสนอให้ทิ้ง" | เมนูครบตามที่เขียนแล้ว การทิ้งเกิดเมื่อ human partner ขอเป็นคำพูดชัดเจนเท่านั้น |
| "'เออ ทิ้งไปเลย' นับเป็นการยืนยัน" | มีแต่การพิมพ์คำว่า `discard` เท่านั้นที่อนุญาตให้ลบ |
| "PR ขึ้นแล้ว worktree เลยเป็นของรก" | ข้อเสนอแนะของ PR ถูกแก้ใน worktree นั้น มันอยู่จนกว่างานจะลงปลายทาง |
| "worktree อื่นนี่ดูค้าง — ล้างด้วยเลย" | ล้างเฉพาะ worktree ใต้ `.worktrees/` หรือ `worktrees/` อย่างอื่นเป็นของโฮสต์ |
| "ลบถูกปฏิเสธ — `--force` แค่ทำการล้างให้จบ" | การปฏิเสธหมายความว่ามีไฟล์ที่อยู่ใน worktree นั้นที่เดียว `--force` ทำลายถาวร แสดงให้ human partner เห็นแล้วถาม |
| "ผลที่ merge ล้มเหลวน่าจะเป็นแค่เทสต์ไม่นิ่ง" | ผลที่ merge ล้มเหลวหยุดทุกอย่าง branch และ worktree อยู่ที่เดิมระหว่างสืบสวน |
| "base branch ก็ต้องเป็น main อยู่แล้ว" | ยืนยันจุดแตกหรือถาม การ merge เข้า base ผิดแก้คืนยาก |
| "push ถูกปฏิเสธ — force-push จะแก้ได้" | push ที่ถูกปฏิเสธหมายถึง remote ขยับไปแล้ว สืบสวน force-push เมื่อ human partner ขออย่างชัดเจนเท่านั้น |
